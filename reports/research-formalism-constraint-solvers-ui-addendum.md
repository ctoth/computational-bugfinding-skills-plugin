### Findings so far

1. **Structural difference from the OOPSLA/PLDI split.** In the thesis, Cassius is not a separate synthesis tool set against VizAssert. Cassius is "a formalization of the browser rendering algorithm" that gives Visual Logic specifications their meaning, and VizAssert is the verifier built on it (p.2, items 2-3; Fig 1.1 p.5). The thesis says Cassius "implements the core of CSS 2.1 using the quantifier-free theory of linear real arithmetic (QF-LRA)" (p.2).
2. **Two stated enabling insights** (p.4): (a) "identifying a fragment of CSS that is both expressive and amenable to layout with a *non-deterministic incremental algorithm*. Such an algorithm is naturally expressible in QF-LRA"; (b) "auxiliary uninterpreted functions" for encoding an arbitrary run of that algorithm so that the query is "linear in the size of the web page".
3. Cassius is described as "a feature-rich, declarative implementation of a browser layout engine, consisting of a set of QF-LRA constraints that relate browser inputs (the CSS stylesheet and the HTML document) and parameters (such as browser size and user preferences) to the browser output (the resulting box-based layout)" (p.4). Scope: "cascading stylesheets, generating boxes for HTML elements, and laying out the resulting boxes" (p.4).
4. **Validation numbers differ from PLDI 2018.** Thesis: Cassius tested on "3651 browser conformance tests" against Firefox (p.3; p.7-8: "Cassius matches Firefox's layout in almost all cases, and the few differences identify known bugs in Firefox"). PLDI 2018 (main report F1) reported 1006 tests, VizAssert 915 supported. Evaluation corpus also differs: thesis 51 templates, 414 page/assertion combinations, 38 violations, 21 false positives, 14 guidelines (p.8); PLDI 62 pages, 502 pairs.
5. The fuzzy-to-formal step is named again (p.4): two challenges "where human interpretation and intuition is requried [sic]: identifying the page elements that a particular guideline is relevant to; and formalizing high-level design principles such as visual importance, alignment, and spacing." Testing informal guidelines "fundamentally requires human interpretation" (p.3).
7. **Ch5 pp.41-55 (read).** Cassius is "a symbolic browser" (p.41) that, unlike an imperative browser, "can perform the layout computation both forwards and backwards: it can not only compute a layout from the parameters, but it can also compute the parameters from a desired layout" (pp.41-43). Inputs are S-expressions with holes `?`, holes may be constrained, e.g. `:font-size (between 16 32)` (p.43, Fig 5.2 p.44). General input: "a stylesheet, a set of document-layout pairs, a set of symbolic browser parameters, and a set of LRA *assertions* on the holes"; Cassius fills holes "so that the resulting concrete stylesheet simultaneously renders each document to its layout, while satisfying the provided assertions" (p.43). Tools are built "by reducing a development task—such as repairing a broken stylesheet—to the problem of completing holes"; Cassius "either completes the holes or returns an explanation for why a completion does not exist, given in terms of CSS constraints" (p.43). Uses as stated: verification (fix elements E and rules R, solve for boxes B), synthesis (fix B and E, sketch R), debugging (fix E, R, B and compute unsatisfiable cores) (p.45). "This work is concerned mainly with verification"; debugger and synthesizer are prototypes in §10.3 (p.43).
8. Source of the formalism: "Cassius derives its specification of CSS layout from the W3C CSS 2.1 standard", which describes CSS "via an abstract algorithm"; Cassius "is a specification of this abstract layout algorithm" (p.45). Machine-readable at github.com/uwplse/cassius (p.45 fn 1). Block layout: "distills 36 pages of the CSS standard into just 790 lines of code" (p.52).
9. Declarative instead of sequenced: imperative browsers compute widths top-down and heights bottom-up; "Because the Cassius semantics is declarative, it dispenses with the need for sequenced computation ... it simply constrains the final value of each property with a formula", e.g. ∀b, block-box(b) ∧ in-flow(b) ⟹ b.x = b.parent.left-content-edge + b.margin-left (p.51).
10. What is left out, and why (pp.46-53): font metrics, line breaking and hyphenation are omitted as "difficult to formalize but easy for a client tool to provide" (p.46); text box width/height must come from client tools "for example by rendering the text and measuring its size" (p.47 fn 3, p.53); only a subset of selectors; "Our implementation simply ignores unknown CSS properties—they can appear in an input ... but their semantics will not be considered by the underlying SMT solver" (p.46). Line breaking: CSS 2.1 does not constrain it, so Cassius relies on pre-broken lines; this "does not affect either synthesis or debugging ... It may, however, cause a verification tool to produce false positives ... We have found such false positives to be rare in practice (see Section 9.2)" (p.52). Opaque boxes are an "escape hatch": position "not related to any CSS properties or to any other boxes"; "This lenient encoding ... ensures that we allow any likely behavior of unknown CSS properties. Client tools can use assertions to constrain the behavior of these boxes" (p.53). Tables are an example of opaque-box content (p.51).
11. Floats (pp.53-55): the standard's nine rules in §9.5.1 (seven properties plus two optimization criteria) are listed (pp.54-55). Two encoding problems: pairwise rules give "too many constraints", and "encoding the optimization criteria introduces quantifiers, which moves the constraints beyond the capabilities of current SMT solvers" (p.55). Each float constraint would be O(|B|²) in quantifier-free logic (p.55). "Cassius initially only allowed restricted uses of floating layout", later lifted by exclusion zones (p.55).
12. **What the first Cassius did that later work changed (pp.56-59).** "To enable efficient automated reasoning, the first Cassius semantics imposed four restrictions on floating boxes" (Fig 5.4 p.56: overlapping floats with text wrapping both; horizontally stacked floats where the later is smaller; a wide second float wrapping while text still fits beside the first; text between a left and a right float). These ensured "the layout of every box depends only on the layout of the floating box closest to it in an in-order traversal". The author's own judgement then: "We did not believe these restrictions to be onerous, since the forbidden layouts can be often be achieved by adding extra elements to the document. However, later work on professional web page templates Section 9.2 required more comprehensive support for floating layout and thus a lifting of these restrictions" (p.57). Fig 5.4's caption: "any layout is achievable despite these restrictions, as long as the HTML is modified" (p.56). Exclusion zones (Y, L, R) replace the set of all preceding floats: a box p is excluded when p.y < y ∨ (p.x < ℓ.x ∧ p.y < ℓ.y) ∨ (p.x > r.x ∧ p.y < r.y) (p.57). The two optimization criteria are met by trying the finite candidates Y ∪ {y*} in increasing order; x for a left float is a member of {x_l | (x_l,y_l) ∈ L} ∪ {p.left[content]} (pp.58-59). So the formalism was first bent to the solver by restricting the domain (forbidding inputs), and the restriction was removed when real inputs (templates) violated it.
13. **Ch6 pp.60-67 (read).** VizAssert "is built atop the Cassius framework": it passes the page "with a fully symbolic layout" and holes for the browser parameters to Cassius "along with the assertion ¬P"; if a completion exists it becomes "a concrete counterexample layout ... presented to the developer", otherwise "all possible layouts of the page are guaranteed to satisfy P" (p.60; Fig 6.1 p.61, a window width `(between 200 1920)` yielding a counterexample at width 400).
14. Two-level encoding (p.62): the semantics is written "declaratively, as a set of formulas in the machine-readable SMT-LIB2 format", with quantified formulas; this "has the advantage of being easy to audit for correspondence to the CSS standard. But it does not consistute [sic] a practical implementation". For solving, inputs "instantiate (or, ground) the quantifiers", producing QF-LRA, simplified, sent to Z3, and the output "is used to either fill the holes in the input or explain why a solution does not exist" (p.62). Naive grounding is O(|B|²) and "overwhelms the solver"; auxiliary uninterpreted functions (e.g. `containing-block`) with axioms using "at most one universal quantifier" give an equisatisfiable encoding linear in |B| (pp.62-63). This "hinges on finding a small set of auxiliary functions that are both efficiently axiomatizable and sufficient ... Intuitively, this means choosing a subset of CSS that can be laid out with a *non-deterministic, incremental* version of the abstract layout algorithm"; the auxiliary functions encode what the incremental algorithm would track "given a correct (angelically chosen) order in which to traverse the tree of boxes" (p.64).
15. Solver-facing details (pp.64-65): a custom formula optimizer "avoids simplifications that interfere with unsatisfiable core extraction, and embeds metadata ... (using Z3's named constraints)" to "lift the solver's output into a solution to the declarative layout problem" (p.64). Multiplication (percentages) is not in QF-LRA; "since in Cassius the stylesheet is generally known, the set of possible percentage values ... is statically known", so a×b becomes a finite case split over constant multiplicands, "placed back within LRA" (pp.64-65). Finitization reductions (p.65): solvers cannot reason efficiently about arbitrary-size sets ("would require induction and therefore invariant synthesis"); Cassius reduces them to finite data structures for line heights, margin collapsing, exclusion zones, "percentage dependency loops, computing containing boxes, and resolving inheritance". Line height is a running maximum (p.67), as in the PLDI paper.
16. **Ch6 pp.68-75 (read).** Margin collapsing becomes six reals and a boolean (pp.69-71), as in PLDI. The author on the standard's rules: they "may look somewhat haphazard and arbitrary. This is because they embed a deep understanding of the sorts of designs that web designers look to achieve ... In any case, arbitrary or not, Cassius must model this semantics faithfully" (p.69). Exclusion zones have canonical forms (Theorem 6.1, pp.72-73); bound k with |L|,|R| ≤ 5 sufficing "for most web pages that we have tested" (p.73); soundness by asserting on every addition that k suffices and retrying with more registers, terminating because the number of floats bounds it (pp.72-73). Validation (p.74-75): "Each time VizAssert runs, it proves that its implementation satisfies the standard's rules for floating layout, for the current k. If the proof fails, VizAssert retains soundness by terminating"; each of the nine rules is proved by induction over exclusion-zone construction, by the SMT solver; "We have performed a paper proof that this automated proof always succeeds" (p.75). The thesis attributes exclusion-zone machinery to Cassius in Ch5 (pp.57-59) and to VizAssert in §6.4 (pp.73-75).
17. **§8.2 pp.93-100 (read).** Cassius placed against constraint-based layout: ConstraintSS [BBMS99] lets authors write constraints with priorities and uses Cassowary [BBS01] as the solver (pp.93-95). The thesis's general verdict on constraint-based layout: conflicts and ambiguity can be resolved "(such as with priorities and objective functions) but also obscures some of the benefits (like ease of analysis and predictability) of constraint-based layout" (p.95). The contrast it draws: "Like ConstraintSS, Cassius models CSS as a set of constraints that are solved to lay out the page. However, Cassius does not replace CSS or modify existing browsers. Instead, it provides a mechanized semantics for CSS, and as such, it could potentially be used to compile constraint-based layout languages to CSS" (p.95). (The thesis describes Cassowary as minimizing "the product of the 'error' for each linear constraint ... multiplied by a representation of the priority" (p.95); that is the thesis's paraphrase, not checked here against the Cassowary paper's own definition beyond what the main report F2 records.) pbrowser (attribute grammars) "cover a smaller subset of CSS than Cassius" and "are not meant for verification, only layout" (p.99). No section of 8.2 compares Cassius with VizAssert; they are presented as layers of one system throughout.
18. **§9.1 pp.107-109 so far (read).** Purpose: show "the Cassius semantics faithfully models the CSS standard and that its encoding to LRA is efficiently-solvable by comparing it to Mozilla Firefox on a set of 3651 standard browser conformance tests" (p.107). Two experiments: (a) acceptance: feed Firefox's concrete layout and check Cassius allows it, showing the semantics is "*sufficiently weak*"; Cassius agrees "on all but 15 tests, on which Cassius produces correct layouts according to the standard, while Firefox produces slightly different layouts due to rounding errors or known bugs" (p.107); (b) "solver-aided mutation testing" for rejection, showing the semantics is "*sufficiently strong*": "Only 0.7% of mutants are accepted by Cassius, largely due to font metrics, which Cassius does not model" (p.107). Oracle: Firefox 60.6.1, "since volunteers have already checked that Firefox passes these tests"; layouts extracted via a CSSOM script (p.108). The W3C tests are pages with "an English-language description of the expected output" and a reference page; the Cassius fragment is covered by 3651 tests; tests "rarely consist of more than a dozen elements" (p.108). Acceptance tests exercise the encoding "even with fully concrete inputs: Cassius uses the solver to search for a trace of its non-deterministic layout algorithm that admits those inputs" (p.108). Table 9.1 (p.109, continues): rejects 1 in §8.3.1 collapsing margins, 10 in §8.5.1 border width.
19. **§9.1 pp.110-113 (read).** Table 9.1 totals (p.111): Accept 3463, Reject 15, Unsupported 164. Run on an i7-4790K with Z3 from the `opt` branch of 11 March 2015; whole suite 178 minutes, "less than four seconds per test" (p.111). The 164 failing tests "use unsupported features, most prominently vertical alignment, right-to-left text, and SVGs" (p.111). The sections needing finitization reductions (10.8/10.8.1 line height, 8.3/8.3.1 margins, 9.5/9.5.1/9.5.2 floats) are called out (p.111). Disagreements: "Among the passing tests are 15 for which Cassius's layout is different from Mozilla Firefox's. On 11 tests, the cause ... is rounding error within Firefox ... On the other 5 Firefox's behavior ... is known to be incorrect" (p.111). Firefox rounds to 1/60 px and rounds border widths and text positions to whole pixels; "Since Cassius uses real (infinite-precision) arithmetic, per the CSS standard, its specification does not admit this rounded value" (p.112). **Internal inconsistencies in the thesis, as printed:** p.111 says Cassius "agrees with Firefox on all but six", the next paragraph says 15, and 11 + 5 = 16, not 15; p.107 says "all but 15". By my arithmetic Table 9.1's totals sum to 3642, not the 3651 stated (pp.107-108, 111). I report these as printed and do not resolve them.
20. Rejection (mutation) tests (pp.112-113): "run during the development of Cassius. Since it was run on an older version of Cassius, its results are not directly applicable to Cassius's current form". 2075 acceptance tests; one block-box width/height/x/y replaced by a hole; Cassius asked for a layout differing from Firefox's in that measurement; ten times per test, 20,750 attempts. Accepted 152 (99.3% rejected): 126 because "Cassius does not model font rendering" (it "accepts layouts that subtly move the boundary between two lines of text"), 26 from "non-determinism in the CSS 2.1 algorithm for computing the shrink-to-fit width of floating boxes", where "Cassius treats the non-determinism in the specification by accepting several layouts" (p.113). The validation therefore tests the formalism in both directions against an independent implementation: not too strong (accepts Firefox's layouts) and not too weak (rejects mutated ones).
21. §9.2 opening (p.113, read only this page of §9.2): the 51 templates were the subset, of the 100 most recent FreeWebsiteTemplates pages, "that fit within the subset of CSS supported by Cassius".
22. **Ch10 pp.132-136 (read).** Coverage (p.132): "CSS is large: dozens of standards totaling thousands of printed pages"; vertical alignment and right-to-left text "would only require engineering time"; text-align, overflow, white-space, box-sizing, text-indent and list-style-position were each added "with minimal changes to the semantics and required only a few hours each"; yet "it is likely neither feasible to completely formalize all of the minor features available in modern browsers, nor keep up with future additions". Tables are "the most important" research challenge (pp.132-133); flex-box and grid are named as increasingly important (p.133). Extensions (p.133): "Cassius-like approaches could also be applied to formalize mobile and desktop GUI frameworks. Alternatively, constraint-based frameworks (such as the iOS Cassowary framework) could be compiled directly to SMT formulas (including specialized handling for priorities)"; JavaScript and server-side code are out of scope (p.133).
23. **Debugger and synthesizer (§10.3, pp.134-136): what returns to the user.** Debugger: inputs concrete stylesheet C, document D, layout B and the parameters v⃗ violating P; replace each v_i with a hole h_i and assert P(h⃗) ∧ ⋀ h_i = B(v_i), which is unsatisfiable by construction; "Invoking Cassius on such a problem produces an unsatisfiable core—a small subset of the constraints in C, and in the CSS semantics, that is responsible for the violation"; the debugger "projects this core onto C and pretty-prints it" (p.134). Fig 10.1 (p.135): the localized fault names both *set* properties (div's float) and *unset* properties (main's float and height), shown as strikethrough/bold in the user's own stylesheet. Synthesizer (CSS sketching): a stylesheet with expression holes plus document-layout examples; expression holes reduced to numeric holes by "a standard reduction [SLTB+06]"; solutions lifted back to a stylesheet; it repairs Fig 6.1's stylesheet, and "the synthesizer ultimately decides not to set the height property" (pp.135-136, Fig 10.2). These are labelled prototypes (p.43) and the thesis gives no evaluation numbers for them in the pages read.
