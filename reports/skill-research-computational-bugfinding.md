## Established primary-source findings

- **Generation, instrumentation, and correctness oracles are separate decisions.** Go's fuzzer supplies coverage-guided inputs and minimizes failures; its assertion body determines the property. Targets must avoid cross-invocation global state. Actual coverage instrumentation currently needs AMD64 or ARM64. Source: https://go.dev/doc/security/fuzz/ (Writing fuzz tests; Running fuzz tests; Failing input).
- **Hypothesis supports programs, not just values.** Rule-based state machines can compare a real system against a simpler model, carrying generated objects across operations through bundles. Source: https://hypothesis.readthedocs.io/en/latest/stateful.html (Rule-based state machines; Rules).
- **Native fuzzing is already covered locally.** Installed `golang/go-testing-advanced` includes native fuzzing, seed corpus persistence, benchmarks and Go synctest; copying that guidance would not establish new capability.
- **AFL++ campaigns involve instrumentation and corpus preparation, not merely more random bytes.** Its in-depth guide explicitly covers sanitizers, corpus minimization, multiple cores, coverage, beyond-crash oracles, and crash triage. Sources: https://aflplus.plus/docs/ and https://aflplus.plus/docs/fuzzing_in_depth/.
- **Valgrind is dynamic instrumentation, not an input generator.** Memcheck's quick-start demonstrates invalid memory access and leak reports; it warns about substantial runtime overhead and optimized-build diagnostic limits. Source: https://valgrind.org/docs/manual/quick-start.html.
- **Race detection is observation-dependent.** Go exposes `-race` for tests/builds/runs; the report identifies conflicting accesses and goroutine creation. It is not an assertion of arbitrary logical concurrency correctness. Source: https://go.dev/doc/articles/race_detector.
- **Schedule exploration is a distinct capability.** Coyote rewrites C# IL and controls concurrency, returning replay traces. Loom permutes Rust executions using its own concurrency types, with explicitly documented unsupported memory-model behaviors that can yield both false alarms and missed executions. Sources: https://github.com/microsoft/coyote and https://github.com/tokio-rs/loom.
- **Jepsen, Elle, and Porcupine have different jobs.** Jepsen generates histories while injecting real-cluster faults; Elle analyzes transaction dependency anomalies; Porcupine checks histories against an executable sequential model for linearizability. Sources: https://jepsen.io/analyses, https://github.com/jepsen-io/elle, https://github.com/anishathalye/porcupine.
- **Semantic database testing goes beyond crashes.** SQLancer documents result-correctness, internal-error, crash, and selected performance oracles; Java 11+ and Maven are its documented minimum build requirements. Source: https://github.com/sqlancer/sqlancer (Getting Started; Using SQLancer).
- **Symbolic and bounded exploration are concrete options.** KLEE explores LLVM code symbolically; CBMC unwinds C/C++ programs into solver queries and checks assertions/memory/undefined behavior. CBMC also points to JBMC and Kani for Java/Rust. Their explored model and bounds delimit any assurance. Sources: https://klee-se.org/ and https://www.cprover.org/cbmc/.
- **Elle literature insight:** the generator can deliberately choose data representations that make executions easier to check. Unique append-only values reveal version order and write provenance, enabling dependency witnesses. This is a stronger design lever than adding CPU to an uninformative workload. Elle excludes predicate analysis and its completeness depends on observable information and recoverability. Source: Kingsbury and Alvaro (2020), local paper images pp. 2-8, 12-13; https://arxiv.org/abs/2003.10554.

### Capability advances to investigate, with concrete Barn applications

These are **research-derived candidates**, not findings that Barn is defective or assertions that no other worktree already implements them. No full-repository absence proof was attempted.

1. **State-aware semantic generation beyond the existing valid-IR generator.** The strongest inspected baseline already constructs valid MOO programs and requires compilation. Its expression generator does not establish a dependent type/environment proof for each operation, and its executor starts from an empty store. A meaningful advance is reaching deep, successful, stateful object/permission/verb paths with generated worlds and runtime-valid API sequences, then shrinking world+program together. Measure semantic progress and property reach, not only successful parsing. This requires direct source work, not installing Csmith or repeating the current generator design.
2. **Differential dimensions beyond the existing string-corpus Toast replay.** The baseline already compares compilation, values and error codes. Investigate the configured omission of structured-choice corpus replay, world effects and per-case equivalent state, scheduler/fork/suspend behavior, persistence boundaries and supported non-ASCII contracts. These are **coverage questions, not verified defects**. Add independent metamorphic relations or references where the contract supports them, with explicit preconditions for effects, overflow, floating point, quotas and intended engine differences. A disagreement is a candidate requiring adjudication.
3. **Systematic schedule search beyond held pairs and random rounds.** Existing Elle tests already force several interleavings. Explore operation sequences *and* controlled decisions around validation/publication/retry/irreversible boundaries, with replayable choice traces and reduction of both schedule and workload. Loom/Coyote/Shuttle demonstrate runtime-specific approaches; **none was verified as a drop-in Go scheduler controller**. Go synctest virtual time alone must not be advertised as exhaustive schedule exploration.
4. **Persistence/crash consistency at real failure boundaries.** Existing database tests normalize completed round trips. Test a disposable server's acknowledged operations against recovered state while exploring interruption, partial writes, flush/rename failure, disk-full and restart points, using the documented persistence guarantee as oracle. Do not infer durability guarantees from in-memory serializability or claim SIGKILL simulates every power-loss model. This needs deeper persistence-source and filesystem-model research before implementation.
5. **Liveness and resource search with quantified contracts.** Existing VM tick limits and string watchdogs detect selected stuck work. Search input-size families and workload sequences for superlinear CPU/allocation growth, goroutine/handle retention, starvation and unbounded retries. Preserve cold/warm states and distinguish expected quota rejection from an exhausted harness/host. Repeated matched measurements and a stated threshold are necessary before calling a performance anomaly a bug.
6. **Oracle sensitivity measured against defects.** Barn already has twenty strong Elle fault controls. Extend the *principle* to other oracles with representative known defects or independently justified mutants: demonstrate the harness reaches and rejects a defect, then uses the same oracle on the target. A high mutation score is not evidence that every behavioral contract is covered; avoid tests that just validate the harness's own assumptions.
7. **Solver-assisted hard paths and bounded invariants.** Use symbolic/concolic/BMC methods where a small relevant target and trustworthy model exist. For Barn's pure Go code, KLEE/CBMC are not drop-in tools. Identify supported-language dependencies, small extracted specifications checked against real executions, or Go-specific tooling during per-skill research; don't propose a second implementation merely to make a solver run.
8. **Budget allocation on useful evidence.** Barn already consumes a bounded nightly budget and preserves failures. A next campaign can measure marginal unique, reproducible defects, oracle/semantic reach, accepted executions, reduction cost, and duplicate/infrastructure rate. Shift effort among targets, dictionaries, generators and oracles based on observations. CPU hours, corpus count, coverage increases and LLM-generated reports are not interchangeable with confirmed defects.

## Standards and specifications

There is no single normative computational-bugfinding standard in this evidence set. A campaign's correctness claim must come from the target's language/runtime/API/storage/consistency contract, with its enabled configuration. Tool documentation defines what the search and checker actually observe. Isolation models, linearizability, language undefined behavior, and persistence acknowledgments are different contracts. The Elle paper and official Jepsen/Porcupine documentation establish why these cannot be collapsed into a generic pass/fail notion.

## Established practices and unresolved areas

### Practices supported by this evidence

- Couple generation with a property strong enough to reject wrong answers. SQLancer and Elle show alternatives when a conventional expected-output reference is unavailable.
- Make state, nondeterminism and boundaries explicit. Go fuzz guidance requires isolated inputs; Coyote/Shuttle require controlled execution to replay schedules; FoundationDB's simulation depends on a compatible runtime.
- Preserve the actual failing input, source/binary/configuration, seed or decision trace, raw outputs and witness. A seed does not replay external scheduling automatically.
- Shrink while preserving the **same** property violation, valid-input requirements and causal behavior. A smaller crash with a different cause does not establish the original result.
- Use negative controls to measure whether the oracle would detect representative faults. Barn already supplies a useful real example; do not mistake it for new capability introduced by the plugin.
- Distinguish test failure, unsupported case, intentional implementation difference, harness bug, infrastructure failure, unknown checker outcome, and confirmed product defect. `scripts/check_elle.py` supplies a real explicit-outcome example.

### Areas identified for deeper per-skill research

- Metamorphic relation derivation and preconditions; semantic-preserving compiler transformations; coverage-guided structured/API sequence mutation; concolic hybrid selection; grammar inference; taint/data-flow guidance.
- Crash/power-loss models, filesystem failure injection, acknowledgement/durability boundaries, and reduction of fault sequences.
- Numerical accuracy and stability oracles (high precision, tolerances, NaN/signed zero), side-channel/leakage or constant-time testing, adversarial complexity search and resource leak detection.
- Protocol/state-machine fuzzing, GUI/browser event sequences, kernel/syscall fuzzing, schema/spec-derived API tests, combinatorial configuration testing and cross-architecture/build-mode differential testing.
- LLM-assisted harness generation, oracle proposals and triage: useful candidate producers, requiring compiled/runnable harnesses and independent evidence. The Google OSS-Fuzz-Gen repository was located, but no empirical effectiveness claim is made from its title or unreviewed results.
- Mutation testing as oracle adequacy, not a direct count of shipped product bugs.

These topics should not be excluded merely because one general-purpose fuzzer exists. Their method-specific tool details and foundational papers remain unverified at Phase 1 and must be resolved where selected for drafting.

## Gap analysis

### Model already knows well

No benchmark of this model's competence was performed. Treat claims about baseline knowledge as design judgment, not evidence. Generic definitions of fuzzing, table-driven tests, the happy-path Hypothesis example, and `go test -race` syntax are low-value content here because capable agents and existing installed skills already supply them. The user's Barn source establishes a substantially higher bar than those basics.

### Needs explicit guidance

- **Choose the missing search dimension.** Is the blind spot data shape, semantic property, operation order, scheduler choice, failure boundary, configuration, numeric range, or resource growth? More of the same mutations cannot repair a missing oracle or excluded capability.
- **State the guarantee and its preconditions.** Equivalent results require matched configurations, state and specified semantics; linearizability is not serializability; memory-race freedom is not logical correctness; completed round trips are not durability.
- **Invest in informative generation.** Elle's traceable objects and SQLancer's result oracles show that representation/workload design changes what evidence is obtainable.
- **Reproduction includes nondeterminism.** Store a replayable sequence/trace where available, not only a random seed. Preserve failed reduction attempts and inconclusive cases.
- **Triage must not manufacture certainty.** An LLM can inspect witnesses, group likely duplicates, propose causes and identify missing evidence. A confirmed finding requires a real producer and violated contract; LLM confidence or majority agreement cannot substitute.
- **Allocate compute against evidence quality.** Distinguish unique defects, duplicates, semantic reach, throughput, CPU cost, reduction/triage cost, infrastructure loss and zero findings. No bugs found within a budget is a valid result, not correctness proof.

### Needs tooling

Coverage/sanitizer instrumentation, generated input execution, reproducible schedule control, crash/fault injection, solver queries, dependency/history analysis, deterministic reducers, resource measurements, and artifact preservation cannot be established from prose review alone. Tool applicability must be checked per actual runtime/build/platform rather than extrapolated from its language family.

### Not covered by inspected installed skills

The inspected skills do not provide the integrated advanced method selection/oracle design/campaign-evidence workflow above. This is a bounded observation, not an exhaustive negative claim over every installed file. The strongest new value is carrying a target from its present demonstrated capability into a specific unsearched failure space with a working oracle and replayable counterexample.

## Human experience, testing reality and process integration

Users suffer silent corruption, lost work, incorrect answers, hangs and degraded service; developers suffer unrepeatable failures, flood-like duplicate reports and weeks spent on harness defects. Those outcomes are better acceptance targets than a tool having run. Reports should explain the observable trigger, expected contract, actual result, reproduction, scope and uncertainty in plain language.

Local pilot work, finite CI regression, long discovery campaigns, sensitive evidence retention and externally published findings need distinct invocation boundaries. Discovery artifacts should remain usable by a maintainer who did not run the campaign. A plugin must not infer authority to spend cloud money, attack a production service, publish an issue, or edit a target merely because it was asked to research techniques.
