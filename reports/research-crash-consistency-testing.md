## Required capability and contract method

This skill should run a bounded durability/recovery investigation from a real producer, rather than recommend generic random restarts. Its entry contract is an actual caller acknowledgment and the production persistence path behind it: API return/response, batching, buffering, write, successful file sync, namespace change, successful directory sync, acknowledgment, and later recovery. Trace all layers used; label each step observed or unverified. Define what the acknowledgment promises under the target's configured storage/OS contract before constructing the oracle. The order above is an example to investigate, not a universal mandated algorithm. Linux file sync does not alone promise directory-entry persistence. [fsync DESCRIPTION](https://man7.org/linux/man-pages/man2/fsync.2.html), [rename DESCRIPTION](https://man7.org/linux/man-pages/man2/rename.2.html).

For each crash point divide operations into acknowledged durable, acknowledged explicitly nondurable, completed with error, and pending/unknown outcome. Specify a **set** of allowed recovered logical states: committed records that must survive, unacknowledged records that may survive or disappear, atomic groups that cannot partially survive, valid old/new namespace alternatives, and independent records that must remain untouched. An uncertain return is not automatically an absent effect. Treat this state-set construction as synthesis from the target contract; do not attribute a generic transaction model to CrashMonkey. The paper's actual oracle compares explicitly persisted objects, not all precrash observations (pp.6-8).

Capture precrash application responses outside the crashed domain, injector event/completion, syscall/I/O return codes and relevant data/image/log snapshots. Recover through the real startup path with the correct files/settings/version, then check data, namespace/metadata where promised, recovery outcome and ability to continue writing. Reopening successfully or passing fsck alone cannot certify user data durability (paper pp.7-8). A completed normalized database roundtrip and in-memory serializability do not supply this failure/recovery experiment. This is an advance beyond the source-read Barn baseline in the domain report; no new Barn absence or bug claim is made here.

## Model selection: actionable supported routes

### Process failure route

Kill only a specifically owned disposable target process at a recorded boundary, reopen its files through real recovery, and call the result process-crash recovery. The kernel and hardware caches remain a different domain; killing the process does not establish a power-loss model. Avoid declaring all unsynced bytes lost. Use this route when it matches the promised failure, or as an explicitly weaker first experiment. This distinction follows from Linux fsync's separate transfer of data to storage and the B3 paper's explicit replayed crash-image model; do not claim a SIGKILL is CrashMonkey's disk-state replay.

### LazyFS: application data-loss/torn-write model through FUSE

- [Pinned README](https://raw.githubusercontent.com/dsrhaslab/lazyfs/d93e54a7944b28e86506d2af3a97342f5c3eb21f/README.md), accessed 2026-11-07: research prototype, C++17/FUSE3; documented ext4/default-mount Debian11/Ubuntu20.04 tests, not a Windows-native route or current distro guarantee. README badge link and text disagree; actual license controls this observation.
- Model unsynced cache loss with `cache.apply_eviction = false`; tune/document cache model and all application I/O paths. Mount and backing tree are distinct owned disposable paths. Unrouted paths bypass injection and invalidate coverage claims. `torn-seq` preserves selected writes from a selected unsynced sequence; `torn-op` preserves selected pieces of a chosen write. Both fault families include LazyFS crashing; record exact file/occurrence/write indices or part sizes and selected persisted pieces.
- [Actual mount script](https://raw.githubusercontent.com/dsrhaslab/lazyfs/d93e54a7944b28e86506d2af3a97342f5c3eb21f/lazyfs/scripts/mount-lazyfs.sh) confirms shape `./scripts/mount-lazyfs.sh -c CONFIG -m OWNED_MOUNT -r OWNED_BACKING -f -s` from the lazyfs directory after supported build. No mount/config/host change executed here.
- README command literal `lazyfs::clear-cache` requests cache loss; optional configured `fifo_path_completed` reports `finished::clear-cache`. Preserve completion event before checking recovery. ## Worked scenarios for the drafter

1. **Replace an acknowledged snapshot.** Producer writes temp snapshot, syncs content, renames over current name and acknowledges. Trace whether directory sync and errors occur before acknowledgment; record actual contract. Enumerate boundary cuts and old/new/partial possibilities permitted by that exact stack. Recovered acknowledged new snapshot missing or mixed is a finding only if forbidden by the contract. Atomic rename's live visibility is insufficient evidence for power-loss durability. Compare complete checksummed logical snapshot plus unaffected files, then perform another real update. For LazyFS verify namespace model before claiming directory-loss coverage; otherwise select verified block/VFS model. [Linux fsync/rename above; paper pp.3,7-9.]
2. **Durable batch versus pending successor.** Persist and externally record acknowledgment for batch A, begin B, snapshot model before graceful close, reopen on crash clone. A must meet actual durability promise; B may be present/absent or have a permitted atomic outcome, not necessarily absent. Vary boundary, operation skeleton, data-range overlap, WAL/checkpoint/rotation path and persisted-subset seed independently. If the configured API offers nondurable acknowledgment, use its actual weaker state set. Pebble API/caller above supports the model route; batch semantics must come from target source, not this report.
3. **Flush error during namespace update.** Select the actual sync/rename operation/path/index using the existing supported seam. Verify an injection counter/event, error propagation through actual caller and no success acknowledgment if target promises durable completion only after successful flush. Recover from the selected model state and verify earlier acknowledged records. A pre-operation errorfs failure does not establish correctness under post-effect EIO, torn writes or deferred ENOSPC. Linux fsync ERRORS documents delayed writeback failures and ENOSPC/EDQUOT; model those only through a route that actually supports their semantics.
4. **Torn record with intact earlier commit.** LazyFS `torn-op` selects a concrete write occurrence and persisted pieces for a real application's encoded record/WAL. Capture actual write boundaries, not logical record sizes alone; buffering can merge/split writes. After model failure, recovery may reject/truncate an uncommitted tail if allowed but must preserve prior promised commits and continue safely. Repeat on fresh equivalent owned baseline, reduce operation/byte/part choices while retaining fault hit and same forbidden recovered effect. Torn corruption is a test of the application's selected fault contract, not a statement every drive produces this state.

## Search, evidence and reduction

Increase compute along explicit independent dimensions: workload length; initial state (new versus existing data); aliases/link/rename/replacement topology; overlapping writes; persistence placements; error operation/index; crash boundary; persisted subset/torn pieces; deterministic seed. Bounded skeleton enumeration can reach small interaction bugs before long random scripts; the paper's reduced path domains and persistence boundaries explain its tractability (pp.5-10). Add rotation/checkpoint/compaction boundaries only when real producer source shows them. Keep filesystem/runtime/settings fixed during one interpretable comparison.

A valid result records exact target/tool pins, OS/kernel/FS/mount/storage model, initial image, real producer operation trace and acknowledgment evidence, faults requested **and hit/completed**, crash state and model, recovery command/config, allowed states and actual violation, raw outputs, and reproduction command. Separate unsupported setup, injector miss, recovery timeout, target error and violated promise. These are research synthesis of the concrete pipeline, not a universal JSON schema requirement.

Reduce workload and initial state with dependency preservation, then reduce fault schedule/cut/subset/byte ranges. Re-run through actual recovery after each reduction; retain the same violated promise and confirmed injection. A smaller case that merely fails to start or loses only unacknowledged data is not a reproduction. Do not merge two findings solely because they lose the same file: the paper's unique-bug claims used code-path inspection (pp.10-13). Specialist failure-reduction/evidence-based-triage skills own general minimization/deduplication; this skill owns persistence/recovery conditions.
