### S3: Go resource observer semantics

[pprof.go at dcc06a82727b447270b1a58cc5f86b49736e317c](https://github.com/golang/go/blob/dcc06a82727b447270b1a58cc5f86b49736e317c/src/runtime/pprof/pprof.go), Heap profile / Allocs profile / `Profile.Add`. Fragment: “as of the most recently completed garbage collection”. Heap profiles are sampled live allocations at that boundary; allocs defaults to cumulative bytes including reclaimed allocations. Neither alone measures native allocations or total process memory. Custom resource profiles retain their key until removal, so incorrectly instrumented tracking can create retention itself. Existing application resource owners are preferable to a new universal tracking registry. The selected source also contains development features; verify target runtime support before selecting any profile. Header declares BSD-style licensing, not a verified full-project license audit.

[metrics/description.go, same pin](https://github.com/golang/go/blob/dcc06a82727b447270b1a58cc5f86b49736e317c/src/runtime/metrics/description.go), CPU class / heap allocation / live-object descriptions. Fragment: “not directly comparable to system CPU time measurements”. CPU-class estimates must not be substituted for billed system CPU. Cumulative allocation, live heap after GC and heap memory awaiting sweep are separate quantities. Choose the metric matching the contract, not the most convenient counter.

[testing/benchmark.go, same pin](https://github.com/golang/go/blob/dcc06a82727b447270b1a58cc5f86b49736e317c/src/testing/benchmark.go), `StartTimer`, `StopTimer`, `ResetTimer`, `runN`, `B.Loop`. ## Proposed method: engineering synthesis from these sources

These are recommended campaign decisions, not a claim that PerfFuzz or pyperf implements a complete resource-contract checker.

1. **Name the real producer and resource promise.** Select a public parser, request handler, database operation or lifecycle entry already exercised by real inputs. Record its validity constraints, permitted size/decoded-size, quotas and expected completion/cleanup. Choose CPU time, latency, allocation churn, retained live objects, process commitment or live resource count explicitly. A legal expensive operation without a budget/correctness promise is an optimization lead, not automatically a bug.
2. **Search structured families.** Vary collision structure, nesting, repetition, decoded dimensions, state cardinality, cancellation/error position and operation histories. Track encoded bytes, decoded size, operation count and concurrency separately. Compare costs at matched relevant sizes; a compressed header can preserve encoded length while changing decoded demand. Existing stateful/semantic generators should supply valid cases. No new generator framework is needed.
3. **Separate fitness from confirmation.** Stable inexpensive operation counts or per-hotspot maxima can retain valuable intermediates without expensive timing on every mutation. Preserve multiple distinct resource/hotspot improvements. Confirm promoted candidates against the actual contract metric on the real path. A branch count is not CPU time; a slow instrumented build is not proof of release-build latency. Schedule broad exploration, matched confirmation and reduction within the same compute envelope.
4. **Make state and observation phase part of the case.** Label cold start, warmed cache, populated state and repeated lifecycle modes. Define creation, use, cancellation/close, draining and quiescence boundaries from actual ownership. Check retained resources after required cleanup before restoring/resetting state. Restarting every operation can erase sequence-dependent retention; never resetting can instead charge intended growing state as a leak. GC is an observation boundary only where relevant to the runtime and promise, not a device to disguise the lifecycle failure.
5. **Confirm with repeated matched observations.** Preserve raw samples and metadata. Match build, runtime, hardware allocation, size, setup and observation phase; alternate/randomize candidate/control order where feasible. Record profiler/tracing overhead separately and repeat uninstrumented confirmation when the claim is about production cost. Inspect distributions and controls to separate transient host load from repeatable candidate behavior. Determine repetition from uncertainty and decision cost, never a universal count or ratio.
6. **Interpret finite growth honestly.** Measure a size/history family, report observed range and effect with uncertainty, and include ordinary valid controls. Finite growth measurements support a bounded observed trend, not an asymptotic complexity theorem. A single huge ratio near timer resolution or one timeout is weak evidence. Keep quota rejection, valid bounded cleanup, harness failure and host-wide exhaustion distinct from the candidate's contract violation. Preserve exact rejection/status/progress evidence and identify who enforced each limit.
7. **Reduce the mechanism and the evidence together.** Minimize input structure and setup/history while retaining validity, size regime, resource phase and repeatable metric violation under matched replays. For a growth claim retain a small family, not just one tiny timeout. Preserve the required number/order of create/cancel/close operations for retention. Recheck controls after reduction; a smaller case that now fails from invalid-input handling or a changed host limit is a different finding.

## Advanced worked scenarios for the drafter

These are proposed scenarios, not observed bugs in Barn or another repository.

- **Collision family at fixed size:** retain cases increasing one chain's comparisons even if total work temporarily falls. Confirm several equal-size colliding/noncolliding families on the real implementation. Reduce keys while preserving collision behavior and contractual input validity. This directly transfers S1's multi-objective insight instead of merely increasing byte length.
- **Repeated cancellation with native handles:** generate acquire/use/cancel/close histories through an existing public owner. Observe acknowledged cancellation and required drain/quiescence, then actual live native handles as well as managed heap. Flat Go or Python heap is insufficient; increased cumulative allocations is also insufficient. Reduce the history while preserving failure-phase placement and post-cleanup live-count growth. S3/S6 establish the observer boundaries; lifecycle design comes from the target's real contract.
- **Warm-state accumulation:** a fresh-process single-call benchmark looks ordinary, while repeated operations on one long-lived subject retain state. Preserve the warmup and history in reproduction, then compare intended bounded cache population with continuing growth after the documented bound. Resetting before the observation erases evidence; never resetting between unrelated candidates contaminates attribution. S3 benchmark reset semantics and S5 worker/calibration distinctions motivate this separation.
- **Compact expanded input:** search valid encoded inputs with independently recorded decoded dimensions, depth and resulting object count. Separate accepted expensive expansion from a promised quota breach. Reduce while preserving the relevant decoded demand and rejection stage. Small file length alone neither establishes unfair work nor guarantees a bounded memory demand. S1 supplies fixed-input-size reasoning; actual limits must come from the target.
- **Noisy timing false lead:** one input times out during host contention but ordinary controls slow similarly. Keep the raw outlier; repeated matched observations determine whether candidate-specific work remains. A stable operation-count increase can guide search without upgrading the original timeout into a proven latency defect. Existing benchmark comparison owners analyze observations; the LLM summarizes evidence and proposes discriminating next cases.
