# Relation design

This pack uses a compact relation description: original domain, transformation, admissible execution conditions, observation/composition and undecidable outcomes. Reuse the project's existing test representation; this is a design aid, not a required schema.

## Preconditions that change the verdict

| Boundary | Inspect before accepting the relation | Concrete source |
|---|---|---|
| Evaluation count and effects | Does a rewrite repeat, omit or reorder an observable computation? | SQLite evaluates BETWEEN's x and a CASE base expression once; an expanded rewrite can evaluate them more often, and CASE uses "lazy, or short-circuit, evaluation" ([expressions, §§6–7](https://www.sqlite.org/lang_expr.html)). |
| State and determinism | Do related runs observe compatible session/data state and deterministic behavior? | SQLite's changes() and last_insert_rowid() "depend on prior SQL statements" and sqlite3_version() can change on upgrade; a function tagged SQLITE_DETERMINISTIC that is not can corrupt an index ([determinism, §§1 and 4](https://www.sqlite.org/deterministic.html)). |
| Composition | Is the relation about bags, distinct sets or function-specific aggregate values? | TLP composes WHERE/HAVING partitions by multiset addition, DISTINCT/GROUP BY partitions by set union, and aggregate partitions as intermediate values ([Query Partitioning, §3, pp.7–11](https://www.manuelrigger.at/preprints/TLP.pdf)). |
| Ordering and duplicates | Which information may normalization remove? | UNION removes duplicates; UNION ALL retains them, and unordered SELECT supplies no row-order promise ([SELECT, §§3–4](https://www.sqlite.org/lang_select.html)). |
| Numeric and empty cases | Are intermediate values, NULL/empty results and rounding still in the admissible domain? | SQLite sum() fails if "an integer overflow occurs at any point during the computation"; with no non-NULL input sum() returns NULL but total() returns 0.0; avg() is computed as total()/count(); without ORDER BY, aggregate inputs arrive in "an arbitrary order" ([aggregates, §§1 and 3](https://www.sqlite.org/lang_aggfunc.html)). "Floating point values are approximate." ([floating point, §1](https://www.sqlite.org/floatingpoint.html)). |

Choose a transformation that changes a relevant implementation path while preserving its stated relation. Adding clauses indiscriminately can suppress the optimization being investigated: the TLP authors note the GROUP BY oracle "might overlook bugs in the handling of WHERE since an optimization might no longer be applicable". Its oracles reached similar line coverage (55.3%–55.9%) yet each found unique bugs, and the authors caution that "coverage information provides only limited insights" ([Query Partitioning, §5.3](https://www.manuelrigger.at/preprints/TLP.pdf)).

Inspect producer and observer separately. TLPWhereOracle builds the variants and preserves reproducer inputs ([producer, lines 44–58 and 141–195](https://raw.githubusercontent.com/sqlancer/sqlancer/a7d60ee450e6a22ca38599c14e984a49773f4745/src/sqlancer/common/oracle/TLPWhereOracle.java)); ComparatorHelper can skip expected errors and observes only the first column of each result ([observer, lines 39–130](https://raw.githubusercontent.com/sqlancer/sqlancer/a7d60ee450e6a22ca38599c14e984a49773f4745/src/sqlancer/ComparatorHelper.java)). A valid transformation does not strengthen that observation automatically.

For a new world/program relation, establish the actual guarantee before proposing renaming, permutation or reordering. This pack's proposed application is to keep mapped identities, visible state and effects together; it does not assert that every language makes such transformations equivalent. Cross-engine semantic matching belongs to `semantic-differential-testing`; precise numerical bounds belong to `numerical-oracles`.
