## Coyote: controlled .NET obligations

The inspected setup lists .NET 10/8/Standard 2 routes and Windows Framework 4.6.2; recheck the chosen artifact and target framework ([installation prerequisites](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/docs/get-started/install.md)). Existing assemblies require the supported rewriting/test-entry setup; static state is shared between iterations: "static state should be appropriately reset before each test iteration" ([Using Coyote, rewriting and test entry](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/docs/get-started/using-coyote.md)).

```text
coyote rewrite EXISTING_REWRITE_CONFIG.json
coyote test EXISTING_TEST.dll --iterations N --max-steps S
coyote replay EXISTING_TEST.dll FAILURE.trace
```

Substitute actual paths and measured iteration/step choices. The documented test entry carries the `[Microsoft.Coyote.SystematicTesting.Test]` attribute; replay consumes the emitted trace ([Using Coyote, Testing options and replay](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/docs/get-started/using-coyote.md)). Unsupported operations need their actual model/replay limits, not an ignored diagnostic: `--no-repro` silences them by "*disabling the ability to reproduce* bug traces", so no `.trace` file is produced ([Using Coyote, Supported scenarios](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/docs/get-started/using-coyote.md)).

A hot/cold monitor expresses pending/satisfied progress. Ending a terminated execution in a hot state is the directly checked half; for infinite executions "we must resort to heuristics", the temperature test ([liveness checking](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/docs/how-to/liveness-checking.md)). Use a fair strategy: "Unfair schedulers have a role to play in finding violations of safety properties, but not in finding violations of liveness properties", and `prioritization` is unfair; with `--max-steps N` the how-to lets fair executions run to 10N steps and flags more than 5N steps in a hot state ([liveness checking, Fair and unfair scheduling](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/docs/how-to/liveness-checking.md)). At the selected source, runtime temperature checks require a fair iteration; the state-monitor counter advances on each such check while hot with threshold above zero, and cold resets it ([runtime](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/Source/Core/Runtime/CoyoteRuntime.cs), [Monitor](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/Source/Core/Specifications/Monitors/Monitor.cs)). The how-to prose instead says it rises when the monitor "transitions to a hot state" ([liveness checking](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/docs/how-to/liveness-checking.md)); the code governs. Warm does not advance that counter. Threshold zero disables this counter check ("If it is 0 then it is disabled"), while the end-of-test hot-state check in `CheckLivenessErrors` still runs ([Configuration, LivenessTemperatureThreshold](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/Source/Core/Configuration.cs), [runtime](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/Source/Core/Runtime/CoyoteRuntime.cs)). Preserve threshold, strategy/fairness, step limits, monitor state and trace; do not call threshold exhaustion a wall-time or infinite-execution proof.

## TLC: a temporal model with a real correspondence

The inspected tool README states "The TLA⁺ tools require Java 11+ to run" and identifies versioned releases; choose the actual existing jar/spec/configuration ([README, Use](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/README.md)). Its supported command entry and trace import/export are documented in USE ([command-line and model-based testing](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/USE.md)); `-config` is defined in the CLI parser, "provide the configuration file; defaults to SPEC.cfg" ([TLC.java, usage](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/tlatools/org.lamport.tlatools/src/tlc2/TLC.java)):

```text
java -cp EXISTING_tla2tools.jar tlc2.TLC -config EXISTING.cfg EXISTING.tla
```

The configuration must select the intended behavior, fairness and temporal property. The shipped clock model makes its weak-fairness premise explicit with `WF_hr(HCnxt)` ([LiveHourClock, LSpec](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/tlatools/org.lamport.tlatools/test-model/examples/SpecifyingSystems/Liveness/LiveHourClock.tla)). Do not copy its configuration as a passing harness: it also checks `PROPERTY ClockSettles` with a `POSTCONDITION PostCondition` that expects a specific counterexample ([LiveHourClock.cfg](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/tlatools/org.lamport.tlatools/test-model/examples/SpecifyingSystems/Liveness/LiveHourClock.cfg), [LiveHourClock, PostCondition](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/tlatools/org.lamport.tlatools/test-model/examples/SpecifyingSystems/Liveness/LiveHourClock.tla)). A model result concerns that abstraction; preserve a mapping from actions/state to the actual producer and test the candidate against real behavior instead of copying production code into another implementation.

Do not use TLC symmetry sets for liveness: doing so "can make TLC fail to find errors" or report nonexistent ones ([symmetry warning](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/toolbox/org.lamport.tla.toolbox.doc/html/model/model-values.html)). Distributed TLC does not check liveness. The help page says "TLC cannot check liveness properties" ([distributed limitations](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/toolbox/org.lamport.tla.toolbox.doc/html/model/distributed-mode.html)), and the code agrees: the distributed application holds only "the invariants to be checked", implied-inits, "the implied-actions to be checked" and the deadlock flag, and nothing in the distributed package runs a liveness checker ([TLCApp fields and checkState](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/tlatools/org.lamport.tlatools/src/tlc2/tool/distributed/TLCApp.java)), whereas non-distributed TLC runs `liveCheck.finalCheck` ([ModelChecker, finalCheck](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/tlatools/org.lamport.tlatools/src/tlc2/tool/ModelChecker.java)). Adding distributed workers therefore cannot fund that check. The symmetry warning comes only from a Toolbox help page, and the README calls the Toolbox "currently unmaintained" ([README, Use](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/README.md)). Record state/action constraints because they prune exploration: TLC "will not explore successor states" of a state violating the constraint ([Spec Options, constraints](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/toolbox/org.lamport.tla.toolbox.doc/html/model/spec-options-page.html)). Graph exploration is followed by final temporal checking; interruption there is incomplete evidence ([ModelChecker, finalCheck](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/tlatools/org.lamport.tlatools/src/tlc2/tool/ModelChecker.java)). The CLI's `-deadlock` disables deadlock checking ("if specified DO NOT CHECK FOR DEADLOCK"); it is not an enable flag ([TLC parser](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/tlatools/org.lamport.tlatools/src/tlc2/TLC.java)).

## Go: fake time and quiescence

Use an existing appropriate synctest test and the project's permitted focused runner. "Time in a bubble only advances when every goroutine in the bubble is durably blocked"; a CPU loop can prevent that, and mutex/I/O/syscall waiting is outside the documented durable-blocking set. When all bubble goroutines are durably blocked, no pending time would unblock one and `Wait` was not called, "there is a deadlock and [Test] panics"; this is a supported deadlock witness for bubble-internal waits only, so a mutex deadlock does not produce it ([synctest, Time/Blocking](https://raw.githubusercontent.com/golang/go/dcc06a82727b447270b1a58cc5f86b49736e317c/src/testing/synctest/synctest.go)). An execution-budget timeout protects the run but is not automatically the product's promised deadline. This API does not document schedule enumeration; select `schedule-exploration` for controlled-choice search where actually supported.
