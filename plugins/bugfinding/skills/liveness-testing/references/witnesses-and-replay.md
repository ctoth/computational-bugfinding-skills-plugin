# Witnesses, search limits and replay

Use this decision table with the actual producer and contract; the categories are this pack's reporting convention.

| Observed evidence | Supported next conclusion |
|---|---|
| No pending admitted work; workers wait for future input | Check whether this is intended quiescence. Durable blocking alone says less than a violated work obligation ([synctest](https://raw.githubusercontent.com/golang/go/dcc06a82727b447270b1a58cc5f86b49736e317c/src/testing/synctest/synctest.go)). |
| Pending required work, no enabled task, accounted-for environment | Investigate a deadlock witness against the selected controller's enabledness model. CHESS reports "a deadlock whenever this set becomes empty", yet interference in record mode "can result in a false deadlock" ([CHESS, §§4.2 and 4.5](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/osdi2008-CHESS.pdf)). |
| synctest `Test` panics with a deadlock | Every bubble goroutine was durably blocked with no time advance left; confirm the blocked waits are the obligation's producers. Waits on a mutex, I/O or syscalls are not durably blocking and never yield this panic ([synctest, Blocking](https://raw.githubusercontent.com/golang/go/dcc06a82727b447270b1a58cc5f86b49736e317c/src/testing/synctest/synctest.go)). |
| Coyote reports a hot monitor or unsatisfied task monitor "at the end of program execution" | The test terminated with the obligation still pending; this end-of-test check is not the temperature heuristic ([Coyote runtime, CheckLivenessErrors](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/Source/Core/Runtime/CoyoteRuntime.cs)). Confirm the monitor's discharge event matches the contract. |
| Hot temperature or step budget exhausted | Retain a potential nonprogress case and exact bound/fairness. Coyote's hot counter and fair-iteration gate determine what ran ([Monitor](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/Source/Core/Specifications/Monitors/Monitor.cs), [runtime](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/Source/Core/Runtime/CoyoteRuntime.cs)). A reached step bound fails only when `FailOnMaxStepsBound` is set, default `false`; otherwise the iteration ends as `ExecutionStatus.BoundReached` ([runtime, CheckIfSchedulingStepsBoundIsReached](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/Source/Core/Runtime/CoyoteRuntime.cs), [Configuration](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/Source/Core/Configuration.cs)). |
| A documented real deadline exceeded | Compare actual allowed outcomes and environment against that deadline; do not derive a deadline from a tool's heuristic threshold ([Coyote liveness](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/docs/how-to/liveness-checking.md)). |
| Model temporal counterexample | Preserve the cycle, fairness and model/configuration, then establish correspondence; TLC's final temporal stage is distinct from state exploration ([ModelChecker](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/tlatools/org.lamport.tlatools/src/tlc2/tool/ModelChecker.java)). |
| Temporal checking interrupted, or state constraints omit behavior | Report incomplete/pruned scope, not completed liveness assurance ([ModelChecker](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/tlatools/org.lamport.tlatools/src/tlc2/tool/ModelChecker.java), [constraints](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/toolbox/org.lamport.tla.toolbox.doc/html/model/spec-options-page.html)). |

Record the admitted work identity, actual completion/cancellation producer, pending monitor state, threads/tasks and wait dependencies, virtual/wall observations, environment availability, schedule/fault decisions, initial durable state, selected tools/build/model and all bounds. This is a tailored replay bundle: CHESS shows that environmental interference, unreplayed state ("a program state not reset at the end of the previous iteration") and nondeterminism can change a schedule's meaning ([CHESS, §4.2](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/osdi2008-CHESS.pdf)).

For Coyote retain original emitted trace and compatible binaries/configuration; the documented replayer consumes that trace, and a run under `--no-repro` produces none ([Using Coyote, replay and Supported scenarios](https://raw.githubusercontent.com/microsoft/coyote/2202e75a861f4e8a63149366c2e41ea21d73ae54/docs/get-started/using-coyote.md)). For TLC retain the spec/configuration and counterexample; USE provides `-dumpTrace json` and `-loadTrace json` for model-based testing, not a proof that the model covers every implementation behavior ([USE](https://raw.githubusercontent.com/tlaplus/tlaplus/d8fb231de4e4b5d02c1b2ed1ac759c086f694021/USE.md)). Retain unknown and unsuccessful replay attempts.

**Illustrative reduction:** remove an unrelated request while retaining the starving request, its real start/discharge semantics, available core and relevant retry history. Removing the sole promised delivery opportunity or restarting away the retained state changes the liveness claim; TigerBeetle's account demonstrates the restart masking problem ([Resonance](https://tigerbeetle.com/blog/2023-07-06-simulation-testing-for-liveness/)). Reuse `failure-reduction` for mechanics and `evidence-based-triage` for attribution; an LLM explanation does not replace the trace.
