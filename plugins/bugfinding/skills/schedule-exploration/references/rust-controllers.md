# Rust controllers

These conditional recipes assume an existing compatible test integration and authorized execution. Commands use POSIX environment syntax; use the invoking shell's equivalent. Check the selected release and preserve its dependency/build features.

## Loom

Use Loom synchronization/thread types throughout the tested path, with the existing conditional compilation owner. Other nondeterminism needs a fitting controlled seam: random numbers and system calls "must be mocked to be testable by loom". For a configured test: `RUSTFLAGS="--cfg loom" cargo test --test loom_my_struct --release`. A preemption bound (`LOOM_MAX_PREEMPTIONS` or `Builder::preemption_bound`) selects a smaller space; it tells Loom to "prune out interleavings that are unlikely to reveal additional bugs", so it does not make an arbitrary scenario complete ([Writing tests, Running, Large Models](https://docs.rs/loom/0.7.2/loom/)).

Record Builder's thread, branch, permutation, duration and preemption settings independently. For checkpoint replay enable the selected dependency's `checkpoint` feature: without it, checkpoint load/store calls ``panic!("not compiled with `checkpoint` feature")``. Duration/permutation checks occur at checkpoint intervals, not as immediate interruption. The inspected crate is 0.7.2 (`rust-version = "1.65"`, `license = "MIT"`); unreleased loom `master` already declares 1.73, so recheck the chosen release ([Builder](https://docs.rs/loom/0.7.2/loom/model/struct.Builder.html), [0.7.2 loop/checkpoint code](https://raw.githubusercontent.com/tokio-rs/loom/a7033ee06a97c52eb2f8131c095fbea6c6eecba3/src/model.rs), [0.7.2 package/features](https://raw.githubusercontent.com/tokio-rs/loom/a7033ee06a97c52eb2f8131c095fbea6c6eecba3/Cargo.toml)).

Retain `LOOM_CHECKPOINT_FILE` and matching configuration; use `LOOM_CHECKPOINT_INTERVAL=1` to isolate the failing permutation ("The test should fail on the first permutation") before enabling location tracking, which Builder documents as "**very** expensive". A checkpoint is not a substitute for the same starting scenario. Loom's scheduler "is, by design, not fair", so fairness-sensitive spin loops need `loom::thread::yield_now`, not arbitrary sleeps ([Debugging, Yielding](https://docs.rs/loom/0.7.2/loom/), [Builder `location`](https://docs.rs/loom/0.7.2/loom/model/struct.Builder.html)).

Read the selected memory model before attribution: the README documents `SeqCst` accesses "regarded as `AcqRel`", producing false alarms, and load-buffering executions Loom "does not explore". A green bounded run cannot exclude those omitted behaviors ([0.7.2 README, Unsupported features](https://raw.githubusercontent.com/tokio-rs/loom/a7033ee06a97c52eb2f8131c095fbea6c6eecba3/README.md)).

## Shuttle

Use its synchronization/thread/random APIs throughout the chosen path: "all uses of synchronization primitives from `std` must be replaced by their Shuttle equivalents". An existing feature-switched integration can run `cargo test --features shuttle`; wrapping unchanged uncontrolled dependencies is insufficient. The README states "licensed under the Apache-2.0 License"; select a consistent release/API set ([Writing Shuttle tests](https://docs.rs/shuttle/0.9.10/shuttle/), [0.9.10 README, License](https://raw.githubusercontent.com/awslabs/shuttle/855ae5d92a02dd3c02ddd3ca99dfaeb3b5e31d5b/README.md)).

Choose policy intentionally: `check_random(case, iterations)`; `check_pct(case, iterations, depth)`; or `check_dfs(case, Some(max_iterations))`. DFS's optional argument is an iteration count, not depth: with it, DFS will "stop after that many iterations". PCT's `depth` is a "bug depth" (the number of preemptions). No policy proves absence: "Shuttle is not sound (a passing Shuttle test does not prove the code is correct)" ([Choosing a scheduler](https://docs.rs/shuttle/0.9.10/shuttle/), [PCT API](https://docs.rs/shuttle/0.9.10/shuttle/fn.check_pct.html), [DFS API](https://docs.rs/shuttle/0.9.10/shuttle/fn.check_dfs.html)).

Configure per-iteration `MaxSteps` separately from total `max_time`: time "will not abort a currently running test iteration". `FailAfter` fails "(by panicking) after the given number of steps"; `ContinueAfter` begins a new iteration. Unconfigured, "Shuttle fails a test after 1,000,000 steps." Neither outcome alone proves the target violated a progress guarantee. Keep the atomic/lazy-static warnings that `silence_warnings` would hide: they flag behaviors that "may miss bugs or introduce false positives" ([Config](https://docs.rs/shuttle/0.9.10/shuttle/struct.Config.html), [steps](https://docs.rs/shuttle/0.9.10/shuttle/enum.MaxSteps.html)).

Preserve the emitted encoded schedule and replay with `shuttle::replay(case, encoded_schedule)`. Deterministic replay holds only if the case "contains no non-determinism other than that introduced by scheduling"; retain the workload and setup with the schedule ([replay contract](https://docs.rs/shuttle/0.9.10/shuttle/fn.replay.html)).
