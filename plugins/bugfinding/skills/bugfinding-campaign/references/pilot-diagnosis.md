# Diagnose the pilot before buying more search

Use this table on observed pilot artifacts. These are campaign design choices grounded in the cited mechanisms, not a proven optimal allocation policy.

| Observed evidence | Next useful action | Evidence needed to continue |
|---|---|---|
| Desired API has no call path from this harness | Find an existing producer or suitable harness entrypoint | Source/configuration path showing the desired code can execute; "static reachability potential" and dynamic coverage are different ([Fuzz Introspector, overview](https://raw.githubusercontent.com/google/oss-fuzz/156f862e5976b3d23828230a0a5b4fef54074d32/docs/advanced-topics/fuzz_introspector.md)). |
| Input accepts/compiles, but dependent operations mostly reject | Inspect missing state, identities, types and permissions; generate prerequisites with operations | Successful visits to the intended behavior, not merely parsing; joint state/input search has a real precedent that "mutates both the SQL input and the database file" ([SQLite §2 and §4.1.3](https://www.sqlite.org/testing.html)). |
| Interesting operations execute, but only crash/no-crash is checked | Derive a contract-backed result/effect/recovery oracle | An observable contradiction or a representative violation the oracle rejects; wrong results need their own checks: "Most fuzzers only look for assertion faults, crashes", while finding where SQLite "computes an incorrect answer" took different fuzzers ([SQLite §4.1.4](https://www.sqlite.org/testing.html)). |
| Histories omit information needed by the checker | Change workload values/observations or use a fitting oracle | Identify which dependencies can actually be inferred and preserve the witness; blind register writes "destroy history" ([Elle §§3 and 4.3](https://arxiv.org/abs/2003.10554)). |
| Reached paths stall behind comparisons | Investigate a supported dictionary, comparison-feedback or solver lane | A target-compatible mechanism and a concrete pilot; AFL++ offers comparison-splitting ("This technique is called laf-intel or COMPCOV") and CMPLOG instrumentation choices, not universal success ([AFL++ §1.b Selecting instrumentation options](https://raw.githubusercontent.com/AFLplusplus/AFLplusplus/d0070729206a80a9af297b2341edd63f68fdac35/docs/fuzzing_in_depth.md)). |
| Same slow/OOM/failure case repeatedly consumes the run | Reproduce and classify it; preserve evidence before excluding or repairing anything | Separate product resource/progress contracts from runner limits; recurrent blocking failures affect search: a target that "frequently reports a Timeout, Out-of-Memory, or other crashes" is blocked from "finding more interesting issues" ([ClusterFuzz performance, Performance factors](https://raw.githubusercontent.com/google/clusterfuzz/77bbad2432fb931906c523786defac928d12afdb/docs/using-clusterfuzz/workflows/analyzing-fuzzer-performance.md)). |
| Many candidates, little completed reproduction | Allocate to replay, reduction and triage | Reproduction reliability, regression revision range and platform; ClusterFuzz says "the regression range is often the most useful information for triage" ([ClusterFuzz triage, Filtering testcases, Regression revision range and Crash statistics](https://raw.githubusercontent.com/google/clusterfuzz/77bbad2432fb931906c523786defac928d12afdb/docs/using-clusterfuzz/workflows/triaging-new-crashes.md)). |
| Useful property-relevant reach continues | Extend within budget or compare a complementary lane | Preserve counters over comparable intervals; diverse AFL++ configurations are an available tactic ([AFL++ §3.c Using multiple cores](https://raw.githubusercontent.com/AFLplusplus/AFLplusplus/d0070729206a80a9af297b2341edd63f68fdac35/docs/fuzzing_in_depth.md)). |
| Reach plateaus and no new findings appear | Diagnose blind spots, change dimension or stop with a bounded negative result | Record remaining uncertainty; for a target that "has not found any crashes in a while", ClusterFuzz advises examining its performance ([ClusterFuzz performance, When to analyze fuzz target performance](https://raw.githubusercontent.com/google/clusterfuzz/77bbad2432fb931906c523786defac928d12afdb/docs/using-clusterfuzz/workflows/analyzing-fuzzer-performance.md)). |

## Keep the denominators

Record counts rather than only percentages. If one campaign evaluates a property for every input and another skips most inputs, equal execution counts are not equal observations. Seed quality and target progress are explicit integration concerns: seed corpus quality "has a huge impact on fuzzing efficiency", and a target should "make at least some progress" ([OSS-Fuzz integration, Fuzz Target and Seed Corpus](https://raw.githubusercontent.com/google/oss-fuzz/156f862e5976b3d23828230a0a5b4fef54074d32/docs/advanced-topics/ideal_integration.md)).

Keep separate columns in the existing experiment record:

- **Search:** submitted and accepted cases, property evaluations, reached operations/effects, instrumented code coverage where applicable.
- **Findings:** raw candidates, reproduced violations, verified cause groups, harness/infrastructure cases and unresolved observations.
- **Cost:** elapsed time, workers/CPU, peak resources, setup, replay, reduction and triage effort.

This metric selection is the pack's decision aid. Do not claim the columns are interchangeable or empirically calibrated. FuzzBench's coverage distributions support reporting variation, while ClusterFuzz's triage fields support retaining reproduction conditions ([FuzzBench report, Per-benchmark summary](https://raw.githubusercontent.com/google/fuzzbench/3234e151d70f6093272a9b4155e68ee57faf986c/docs/reference/report.md), [ClusterFuzz triage, Filtering testcases](https://raw.githubusercontent.com/google/clusterfuzz/77bbad2432fb931906c523786defac928d12afdb/docs/using-clusterfuzz/workflows/triaging-new-crashes.md)).

## Interpret controls, not just totals

When a new expensive lane claims a property, reuse a known regression or independently justified fault to see whether it reaches and rejects the violation. SQLite documents mutation testing as one way to evaluate tests; that does not make mutation score a product-bug count ([SQLite §7.6](https://www.sqlite.org/testing.html)). Use `harness-sensitivity` for the detailed choice. If the control survives, first check that it actually changes observable behavior: SQLite notes that branches which only affect speed "generate false-positives during mutation testing" ([SQLite §7.6](https://www.sqlite.org/testing.html)). Otherwise investigate the oracle or reach before spending the full allocation.

Preserve campaign-level versus per-case limits distinctly. For example, libFuzzer documents separate `-max_total_time` ("the maximum total time in seconds to run the fuzzer"), `-timeout` and `-rss_limit_mb` options; when an input exceeds either per-input limit, "the process is treated as a failure case". Choose their target-specific values in the execution skill, and record which limit ended an observation so a runner limit is classified before it is reported as a product defect ([libFuzzer 23.1.0 options](https://releases.llvm.org/23.1.0/docs/LibFuzzer.html#options)).
