# JS/TS UI sequences and async callback APIs

Conditional recipes for fast-check commands that drive React components, browser pages or Node callback APIs. They extend the fast-check section of [runtime recipes](runtime-recipes.md) and were not executed by this skill's author. Model-free crawling of a discovered UI state graph belongs to `ui-state-exploration`; controlled promise interleavings belong to `schedule-exploration`. Route general fast-check authoring style (file layout, arbitrary hygiene, `@fast-check/vitest`) to fast-check's official [`javascript-testing-expert` skill](https://raw.githubusercontent.com/dubzzz/fast-check/cd9c1884e8a39fe945600fbcda1ec92d518feaa0/skills/javascript-testing-expert/SKILL.md), which scopes itself to "Testing functions and components, not black-box e2e". Route browser driver and trace mechanics to Playwright's shipped [`playwright-cli` skill](https://raw.githubusercontent.com/microsoft/playwright/95e5dca31981bcd0970165853fcc713269d2433a/packages/playwright-core/src/tools/skills/playwright-cli/SKILL.md).

## Version pins

Read fast-check examples at the released tag v4.10.2 (commit `c77afa82`), not `main`. On 2026-11-09 npm `latest` was 4.10.2 ([npm registry metadata](https://registry.npmjs.org/fast-check)), while `main` carries unreleased breaking commits such as "Rename `asyncProperty` into `property`" ([fast-check commit fd17f486](https://github.com/dubzzz/fast-check/commit/fd17f486fc4c8fce5c1f37ce02278742c56c846b)) and "Drop ability to default import from fast-check" ([commit 33342651](https://github.com/dubzzz/fast-check/commit/33342651123b2b7acfcc594a12b39e94d087a4be)). Check the project's installed version before copying an example. For per-run setup prefer the life-cycle plugin, `fc.assert(property, { plugins: [fc.beforeEach(fn)] })`: its hook runs "before each execution of the predicate" and exists "Since 4.10.0", and the property-level `.beforeEach` is marked deprecated in 4.10.2 ([LifeCyclePlugins source](https://raw.githubusercontent.com/dubzzz/fast-check/c77afa8277a67250d798c52e61343b8ed5fd268b/packages/fast-check/src/check/plugin/LifeCyclePlugins.ts), [AsyncProperty source](https://raw.githubusercontent.com/dubzzz/fast-check/c77afa8277a67250d798c52e61343b8ed5fd268b/packages/fast-check/src/check/property/AsyncProperty.generic.ts)).

## React components: commands over Testing Library

fast-check's todolist example is the primary-source wiring ([main.spec.tsx](https://raw.githubusercontent.com/dubzzz/fast-check/c77afa8277a67250d798c52e61343b8ed5fd268b/examples/005-race/todolist/main.spec.tsx)). Inside the predicate it renders the component afresh, then calls `fc.scheduledModelRun(s, () => ({ model: { todos: [], wrapper }, real: {} }), commands)`. It wraps every mocked API function with `s.scheduleFunction(fn, act)`, so the scheduler resolves responses inside React `act`, and finally compares the DOM list with the mock server's list. Commands wrap user-event calls in `act` and compare the DOM before and after ([AddItemCommand](https://raw.githubusercontent.com/dubzzz/fast-check/c77afa8277a67250d798c52e61343b8ed5fd268b/examples/005-race/todolist/model-based/AddItemCommand.ts)). fast-check documents the reason for the `act` argument: "when testing React applications, one cannot perform updates of states outside of `act`" ([race conditions guide, Wrapping calls automatically using act](https://raw.githubusercontent.com/dubzzz/fast-check/c77afa8277a67250d798c52e61343b8ed5fd268b/website/docs/advanced/race-conditions.md)).

Copy the wiring, not the modeling. In that example the model `{ todos: [], wrapper }` is never updated. `ToggleItemCommand.check` reads the real DOM to admit the command, and its `run` selects `position % nonLoadingTodos.length`, recording the resolved item for `toString` ([ToggleItemCommand](https://raw.githubusercontent.com/dubzzz/fast-check/c77afa8277a67250d798c52e61343b8ed5fd268b/examples/005-race/todolist/model-based/ToggleItemCommand.ts)). Its observation uses `queryAllByTestId` and raw `getElementsByTagName`, not role queries ([Model.ts](https://raw.githubusercontent.com/dubzzz/fast-check/c77afa8277a67250d798c52e61343b8ed5fd268b/examples/005-race/todolist/model-based/Model.ts)). The skill's rules still apply: keep a contract model, recompute admissibility from the reduced prefix, and log every resolved target.

- **Per-run isolation.** Call `cleanup()` for each property run through the `fc.beforeEach` plugin, as the example does with the older hook form. RTL registers auto-cleanup as `afterEach(() => { cleanup() })` only `if (typeof afterEach === 'function')`, and sets the act environment only when global `beforeAll`/`afterAll` exist ([RTL src/index.js](https://raw.githubusercontent.com/testing-library/react-testing-library/20ce75f2907ca0e5c5a8ae595c0e9a4e368c7800/src/index.js)). That hook fires once per test, after all runs. Vitest `globals` defaults to `false`, and its docs note that "some libraries, e.g., `@testing-library/react`, rely on globals being present to perform auto cleanup" ([Vitest globals](https://raw.githubusercontent.com/vitest-dev/vitest/3a76b87324ecb8d25509cd009aa87fbe56819c39/docs/config/globals.md)). Without per-run cleanup, earlier runs' trees stay mounted; RTL warns that skipping `cleanup` "could result in a memory leak" and tests that are not idempotent ([RTL API, cleanup](https://raw.githubusercontent.com/testing-library/testing-library-docs/7c49d046b100e657c64bae78270a5813c1c02eb6/docs/react-testing-library/api.mdx)). Confirm the project's setup makes React's act environment true rather than assuming RTL did it.
- **Interactions.** Drive commands with user-event. It "adds visibility and interactability checks" and "factors in that the browser e.g. wouldn't let a user click a hidden element or type in a disabled text box"; use `fireEvent` only for interactions user-event has not implemented, and label those commands ([user-event intro](https://raw.githubusercontent.com/testing-library/testing-library-docs/7c49d046b100e657c64bae78270a5813c1c02eb6/docs/user-event/intro.mdx)). The docs recommend `userEvent.setup()` before rendering; the fast-check example calls the direct API instead. user-event's default `delay` moves input "to the next macro task and allows other (asynchronous) code to run between events", which is an interleaving point with app work ([user-event options, delay](https://raw.githubusercontent.com/testing-library/testing-library-docs/7c49d046b100e657c64bae78270a5813c1c02eb6/docs/user-event/options.mdx)).
- **Observation.** Prefer role queries; `getByRole` "should be your top preference for just about everything" ([queries, Priority](https://raw.githubusercontent.com/testing-library/testing-library-docs/7c49d046b100e657c64bae78270a5813c1c02eb6/docs/queries/about.mdx)). Record a test-id fallback as a limit. `waitFor` "may run the callback a number of times until the timeout is reached" (default 1000 ms), and `findBy*` is `getBy*` plus `waitFor` ([async methods, waitFor](https://raw.githubusercontent.com/testing-library/testing-library-docs/7c49d046b100e657c64bae78270a5813c1c02eb6/docs/dom-testing-library/api-async.mdx)). A retrying check passes once the expected state appears, so an intermediate wrong state is never asserted. Use retrying queries to wait for a settled state, then assert the full expected observation once with synchronous queries. When the transient state is itself the contract, assert it at a scheduler-controlled point.

## Browser pages: commands over Playwright

No fast-check example drives Playwright; this paragraph is inference from Playwright's documentation. "Playwright creates a context for each test" ([browser contexts](https://raw.githubusercontent.com/microsoft/playwright/95e5dca31981bcd0970165853fcc713269d2433a/docs/src/browser-contexts.md)), not one per property run, so create `browser.newContext()` per run and close it with `BrowserContext.close`; a new context "won't share cookies/cache with other browser contexts" ([Browser.newContext](https://raw.githubusercontent.com/microsoft/playwright/95e5dca31981bcd0970165853fcc713269d2433a/docs/src/api/class-browser.md)). Server-side state behind the page needs its own reset. The whole property shares one test timeout, "30 seconds by default" ([test timeouts](https://raw.githubusercontent.com/microsoft/playwright/95e5dca31981bcd0970165853fcc713269d2433a/docs/src/test-timeouts-js.md)); set the run budget against it.

Actions auto-wait: for `click`, Playwright requires the element to be visible, stable, receiving events, enabled and not inert, and otherwise fails with `TimeoutError` ([auto-waiting](https://raw.githubusercontent.com/microsoft/playwright/95e5dca31981bcd0970165853fcc713269d2433a/docs/src/actionability.md)). A command aimed at a disabled control therefore times out rather than exercising it; give such a command an explicit admissibility check or its own expectation. Auto-retrying assertions "retry until the assertion passes, or the assertion timeout is reached", 5 seconds by default ([assertions](https://raw.githubusercontent.com/microsoft/playwright/95e5dca31981bcd0970165853fcc713269d2433a/docs/src/test-assertions-js.md)), so the masking problem above applies. For the oracle, wait on an app-specific settle signal (designed with `ui-state-exploration`), then take one observation, for example `Locator.ariaSnapshotJSON()` (since v1.63, JS) or role-locator reads ([Locator API](https://raw.githubusercontent.com/microsoft/playwright/95e5dca31981bcd0970165853fcc713269d2433a/docs/src/api/class-locator.md), [locators](https://raw.githubusercontent.com/microsoft/playwright/95e5dca31981bcd0970165853fcc713269d2433a/docs/src/locators.md)), and compare it with the model.

## Node callback APIs: nested call trees

fast-check runs a flat command list. The runner iterates `for (const c of cmds)` and executes `if (await cmd.check(m)) await cmd.run(m, r);` ([ModelRunner source](https://raw.githubusercontent.com/dubzzz/fast-check/c77afa8277a67250d798c52e61343b8ed5fd268b/packages/fast-check/src/check/model/ModelRunner.ts)), and a command exposes only `check(m)`, `run(m, r)` and `toString()` ([ICommand source](https://raw.githubusercontent.com/dubzzz/fast-check/c77afa8277a67250d798c52e61343b8ed5fd268b/packages/fast-check/src/check/model/command/ICommand.ts)). `run` has no channel for a callback's arguments, so `fc.commands` does not generate or shrink a call placed inside an earlier call's callback. A `run` body can still nest calls by hand, but fast-check then neither generates nor shrinks that inner structure. Under `scheduledModelRun`, "Neither `check` nor `run` should rely on the completion of other scheduled tasks" ([race conditions guide, Model based testing and race conditions](https://raw.githubusercontent.com/dubzzz/fast-check/c77afa8277a67250d798c52e61343b8ed5fd268b/website/docs/advanced/race-conditions.md)).

Nessie shows why nesting matters for callback APIs. Some values, such as file handles, exist only inside a callback, and some orderings (read after exists completes) are reached by nesting the second call in the first call's callback (Arteca et al., [ICSE 2022](https://doi.org/10.1145/3510003.3510106), p.1495). Its tests are trees: a call argument may be a pool value, an earlier sibling's return value, a parameter of a callback on the path from the root, or a callback (Defs. 2-3, p.1497). It extends only callbacks that executed in exception-free tests (p.1498). It found callback positions and sync versus async invocation by probing, one callback per probe, so multi-callback signatures are missed (p.1496). Every difference its authors inspected could in principle be exposed by a sequence-only test; nesting reached diverse behavior with fewer tests (p.1502). The paper covers callback-style APIs, not promise or async/await generation.

Pattern (adapted from the paper; not run):

1. Take callback positions from documentation or types. Where neither exists, run the paper's probe once and save the resulting signatures as a fixture.
2. Generate a tree, not a list, with `fc.letrec`. Bound depth with `maxDepth` and a shared `depthIdentifier`, which `fc.option` and `fc.oneof` accept; `fc.array` also accepts `depthIdentifier` ([recursive structures](https://raw.githubusercontent.com/dubzzz/fast-check/c77afa8277a67250d798c52e61343b8ed5fd268b/website/docs/core-blocks/arbitraries/combiners/recursive-structure.md), [array source](https://raw.githubusercontent.com/dubzzz/fast-check/c77afa8277a67250d798c52e61343b8ed5fd268b/packages/fast-check/src/arbitrary/array.ts)).
3. Resolve argument references at execution time: a reference `{ scope: k }` picks `scope[k % scope.length]` from values lexically in scope (callback parameters on the root path, earlier return values), the same modulo selection `ToggleItemCommand` uses. Every shrunk tree then stays well formed. Log the resolved value, because shrinking can change what an index refers to.
4. Each callback records that it ran and its parameters, then interprets its children with the extended scope. Applying the same tree to promise-returning APIs, with children run in `.then`, is an extension the paper does not cover.
5. Report executed nodes, not generated nodes. Children under a callback that never ran, or under a call that threw, did not execute (p.1498). fast-check has no feedback loop, so this count is a measurement, not a generation bias.
6. Await all invoked callbacks with a per-run timeout. A callback that runs twice, never, or after the timeout is an observation; Nessie's difference kinds include a callback called in one commit only (p.1501).
7. Use a contract model per callback where one exists. Otherwise route the paper's commit-to-commit differential (each test run 10 times per commit, output sets compared, p.1501) to `semantic-differential-testing`.

Unexecuted sketch of step 2 (shape only; `apis` and `literal` are placeholders for the target):

```ts
const { calls } = fc.letrec((tie) => ({
  calls: fc.array(tie('call'), { depthIdentifier: 'cb' }),
  call: fc.record({
    api: fc.constantFrom(...apis),
    args: fc.array(fc.oneof(literal, fc.record({ scope: fc.nat() }))),
    inCallback: fc.option(tie('calls'), { maxDepth: 2, depthIdentifier: 'cb' }),
  }),
}));
```

A tree can be the payload of one command when the target also needs flat sequences around it; that command's `toString` must print the resolved tree. Nessie itself is a research artifact: its README says it "has only been tested on linux" ([Nessie README](https://raw.githubusercontent.com/emarteca/nessie/7875cb576ba4ec1ecf23c6ac4ff8f4cdeee7dcf7/README.md)), and the latest commit read is dated 2023-08-05 ([commit 7875cb57](https://github.com/emarteca/nessie/commit/7875cb576ba4ec1ecf23c6ac4ff8f4cdeee7dcf7)). It is not verified on current Node here.
