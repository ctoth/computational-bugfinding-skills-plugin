# JavaScript, Node and React observation channels

Use this reference when a JS/TS harness takes its verdict from a process exit, an unhandled-error event, a test-runner status, a React error callback or console output. Each of these is an observation whose meaning depends on the effective mode, the installed listeners, the runner configuration and the build. Sources were read on 2026-11-09 at the pins in each link; nothing here was executed for this skill. Hydration equality itself belongs to `semantic-differential-testing`.

## Node process: unhandled rejections and uncaught exceptions

**Reports.** Under the default `--unhandled-rejections=throw`, Node emits `unhandledRejection` and, "If this hook is not set", raises the rejection as an uncaught exception. The default uncaught-exception handling prints the stack and exits with code 1 ([Node CLI, --unhandled-rejections](https://raw.githubusercontent.com/nodejs/node/18b32a3b1552e199a01f1a8d9fd64aa756d3b75b/doc/api/cli.md), [Node process, uncaughtException](https://raw.githubusercontent.com/nodejs/node/18b32a3b1552e199a01f1a8d9fd64aa756d3b75b/doc/api/process.md)).

**Depends on.** The mode: `warn` warns "no matter if the `unhandledRejection` hook is set or not", `warn-with-error-code` only sets exit code 1 when no hook is set, and `none` silences warnings. The listeners: with an `uncaughtException` handler installed, "the process will exit with 0" ([Node CLI](https://raw.githubusercontent.com/nodejs/node/18b32a3b1552e199a01f1a8d9fd64aa756d3b75b/doc/api/cli.md), [Node process](https://raw.githubusercontent.com/nodejs/node/18b32a3b1552e199a01f1a8d9fd64aa756d3b75b/doc/api/process.md)). Read the flag, `NODE_OPTIONS` and every `process.on` call in the harness, application, logger and test runner before reading a crash or its absence.

**Misses.** A rejection silenced by a no-op `.catch` emits no `unhandledRejection` at all; only a state or effect observation can see it. `unhandledRejection` fires when no handler is attached "within a turn of the event loop", and a later handler emits `rejectionHandled`, so the set of unhandled rejections is "a growing-and-shrinking list" ([Node process, unhandledRejection and rejectionHandled](https://raw.githubusercontent.com/nodejs/node/18b32a3b1552e199a01f1a8d9fd64aa756d3b75b/doc/api/process.md)).

**Record without changing the outcome.** Node warns "It is not safe to resume normal operation after `'uncaughtException'`". To record errors, use `uncaughtExceptionMonitor`: installing it "does not change the behavior", and "The process will still crash if no `'uncaughtException'` listener is installed" ([Node process, uncaughtExceptionMonitor](https://raw.githubusercontent.com/nodejs/node/18b32a3b1552e199a01f1a8d9fd64aa756d3b75b/doc/api/process.md)). Pair `unhandledRejection` with `rejectionHandled` to keep only rejections that stayed unhandled.

## Test-runner status

**node:test.** Under the default process isolation, a test file runs in a child process and "If the child process finishes with an exit code of 0, the test is considered passing", so the process rules above decide the file's verdict. Async activity that outlives a test is handled, but the runner "does not delay the reporting of test results in order to accommodate it"; `uncaughtException` and `unhandledRejection` events from a completed test "are marked as failed by the `test` module and reported as diagnostic warnings at the top level" ([Node test, Extraneous asynchronous activity and Test runner execution model](https://raw.githubusercontent.com/nodejs/node/18b32a3b1552e199a01f1a8d9fd64aa756d3b75b/doc/api/test.md)). Leaked work that silently mutates shared state raises no event; `harness-sensitivity` covers probing it through test order.

**Jest.** Without `--waitForUnhandledRejections`, "Jest may report false-positive errors (e.g. actually handled rejection reported) or not report actually unhandled rejection (or report it for different test case)". Use the flag when the oracle depends on which test owned a rejection. With `jest.retryTimes`, "Unhandled rejections owned by a test, `beforeAll`, `beforeEach`, or `afterEach` participate in describe retries", so a final pass can follow an observed failure; read the retry reasons ([Jest CLI, --waitForUnhandledRejections](https://raw.githubusercontent.com/jestjs/jest/72614448ecb9d16c58d6474b3091247c14a5c090/website/versioned_docs/version-30.5/CLI.md), [Jest object, jest.retryTimes](https://raw.githubusercontent.com/jestjs/jest/72614448ecb9d16c58d6474b3091247c14a5c090/website/versioned_docs/version-30.5/JestObjectAPI.md)).

**Vitest.** With `dangerouslyIgnoreUnhandledErrors`, "Vitest will not fail the test run if there are unhandled errors" (reporters still print them). An `onUnhandledError` filter makes a filtered error stop affecting the result: "it no longer affects the result of the test run" ([Vitest dangerouslyIgnoreUnhandledErrors](https://raw.githubusercontent.com/vitest-dev/vitest/3a76b87324ecb8d25509cd009aa87fbe56819c39/docs/config/dangerouslyignoreunhandlederrors.md), [Vitest onUnhandledError](https://raw.githubusercontent.com/vitest-dev/vitest/3a76b87324ecb8d25509cd009aa87fbe56819c39/docs/config/onunhandlederror.md)). Read the config before treating a green run as "no unhandled errors".

## React root error callbacks

**Reports.** `onCaughtError` is called "when React catches an error in an Error Boundary"; `onUncaughtError` "when an error is thrown and not caught by an Error Boundary"; `onRecoverableError` when React automatically recovers. By default "React will log all errors to the console" ([react.dev createRoot](https://raw.githubusercontent.com/reactjs/react.dev/7594a2b008489121bdf25f97320d11ac0422510e/src/content/reference/react-dom/client/createRoot.md)). `onUncaughtError` and `onCaughtError` arrived in React 19; React 18 has only `onRecoverableError` ([React CHANGELOG, 19.0.0 and 18.0.0](https://raw.githubusercontent.com/facebook/react/61aa00df822d0eb76d0362eb8b6fdd3527693efe/CHANGELOG.md)). State the React major.

**Depends on.** In React 19.3.1 the default uncaught and recoverable handlers call `reportGlobalError`, which uses `reportError` when it exists, otherwise dispatches a `window` `ErrorEvent`, otherwise calls `process.emit('uncaughtException', error)` ([ReactFiberErrorLogger.js](https://raw.githubusercontent.com/facebook/react/61aa00df822d0eb76d0362eb8b6fdd3527693efe/packages/react-reconciler/src/ReactFiberErrorLogger.js), [reportGlobalError.js](https://raw.githubusercontent.com/facebook/react/61aa00df822d0eb76d0362eb8b6fdd3527693efe/packages/shared/reportGlobalError.js)). Where the error lands therefore depends on the globals of the environment (browser, jsdom, plain Node); check which branch runs. In a development build inside `act`, an uncaught render error is pushed to the act queue and rethrown into the test instead of reaching `onUncaughtError` ([ReactFiberErrorLogger.js, logUncaughtError](https://raw.githubusercontent.com/facebook/react/61aa00df822d0eb76d0362eb8b6fdd3527693efe/packages/react-reconciler/src/ReactFiberErrorLogger.js)).

**Misses.** A custom callback can filter errors; read it before trusting silence. Error boundaries do not catch errors in event handlers, server rendering, the boundary itself or asynchronous code such as `setTimeout` callbacks; those take the ordinary JS route. "In development, the errors will bubble up to `window`"; "In production, instead, the errors will not bubble up", so a global listener sees boundary-caught errors only in development ([react.dev Component, componentDidCatch and Catching rendering errors](https://raw.githubusercontent.com/reactjs/react.dev/7594a2b008489121bdf25f97320d11ac0422510e/src/content/reference/react/Component.md)).

**Record.** Install all three callbacks as recorders, not filters, and keep their output with the replay evidence.

## Console errors and build mode

**Reports.** Many React diagnostics are development-only `console.error` calls. Examples in React 19.3.1: "The result of getSnapshot should be cached to avoid an infinite loop" ([ReactFiberHooks.js](https://raw.githubusercontent.com/facebook/react/61aa00df822d0eb76d0362eb8b6fdd3527693efe/packages/react-reconciler/src/ReactFiberHooks.js)), and the hydration attribute warning "A tree hydrated but some attributes of the server rendered HTML didn't match the client properties", emitted under `__DEV__` only ([ReactFiberHydrationContext.js, emitPendingHydrationWarnings](https://raw.githubusercontent.com/facebook/react/61aa00df822d0eb76d0362eb8b6fdd3527693efe/packages/react-reconciler/src/ReactFiberHydrationContext.js)). Hydration text and structure mismatches are different: after a forced client render they are upgraded to recoverable errors and reach `onRecoverableError` in production too (`upgradeHydrationErrorsToRecoverable`, same file).

**Misses.** A production-build run has none of these messages, so a clean console there says nothing about those contracts. The getSnapshot warning is guarded by the module-level `didWarnUncachedGetSnapshot` flag ([ReactFiberHooks.js](https://raw.githubusercontent.com/facebook/react/61aa00df822d0eb76d0362eb8b6fdd3527693efe/packages/react-reconciler/src/ReactFiberHooks.js)): one message means at least one offender, not exactly one. Record the build mode with every console observation.

## StrictMode

**Reports.** In development, StrictMode re-renders components, re-runs Effects and re-runs ref callbacks an extra time to expose impure rendering and missing cleanup. "All of these checks are development-only and do not impact the production build." ([react.dev StrictMode](https://raw.githubusercontent.com/reactjs/react.dev/7594a2b008489121bdf25f97320d11ac0422510e/src/content/reference/react/StrictMode.md)).

**Misses.** Only the wrapped subtree is checked, and without StrictMode at the root, React "will not re-run Effects an extra time on initial mount". Double invocation covers top-level component logic, "so this doesn't include code inside event handlers" (same page). It is a fixed extra call, not a search over orders. A finding needs the observed difference, such as a duplicated item or a connection count that does not return to baseline after setup, cleanup, setup.

## Worked contract: `useSyncExternalStore` snapshots

**Promise.** "While the store has not changed, repeated calls to `getSnapshot` must return the same value"; a snapshot that always differs means "you will enter an infinite loop" ([react.dev useSyncExternalStore](https://raw.githubusercontent.com/reactjs/react.dev/7594a2b008489121bdf25f97320d11ac0422510e/src/content/reference/react/useSyncExternalStore.md)).

**Observation.** With the store unchanged, call `getSnapshot()` twice and compare with `Object.is`; after a store change, check that the subscriber callback fired and the new snapshot differs. This checks the contract directly and works in production builds (illustrative design, not executed).

**Blind spot.** The development warning above fires once per module, so it cannot replace this check.

## Browser pages under Playwright

**Reports.** `page.on('pageerror')` is "Emitted when an uncaught exception happens within the page"; `page.on('console')` "when JavaScript within the page calls one of console API methods" ([Playwright Page](https://raw.githubusercontent.com/microsoft/playwright/95e5dca31981bcd0970165853fcc713269d2433a/docs/src/api/class-page.md)).

**Misses.** `page.consoleMessages()` and `page.pageErrors()` return up to the "200 last" entries, and their default filter returns only those logged after the "last committed main-frame navigation" (same page). Attach the listeners before the first navigation and keep the full record. Errors caught by application code never reach `pageerror`. Development-only React messages appear in `console` only against a development build.
