# Evidence-based triage

Turn retained observations into a finding another maintainer can assess. Keep **disposition, reproduction and cause** separate: authentic failure evidence can remain unresolved, and a demonstrated contract violation need not have an established root cause. ClusterFuzz records "Reliability of reproducing the crash" as its own testcase field, keeps statistics useful "For a non-reproducible crash", and says finding a culprit from stacks has "no one process to follow" ([ClusterFuzz triage, Filtering testcases, Crash stacktrace and Crash statistics](https://google.github.io/clusterfuzz/using-clusterfuzz/workflows/triaging-new-crashes/)). Use the project's existing records rather than introduce a verdict database.

## Preserve before interpreting

Locate the real producer, original input and raw failure. Retain build/configuration, architecture, instrumentation, invocation and relevant limits; keep starting state, prior operations and controlled choices where the failure depends on them. Link original and reduced artifacts separately; ClusterFuzz itself offers both a "Minimized Testcase" and an "Unminimized Testcase" ([ClusterFuzz glossary, Testcase](https://google.github.io/clusterfuzz/reference/glossary/)). Replay can require the binary "built with the appropriate sanitizer", the bug's timeout or memory limit, and the right word size, since some bugs are "reproducible only in 32 bit mode or only in 64 bit mode" ([OSS-Fuzz reproduction, Fuzz target bugs and Build the image and the fuzzers](https://google.github.io/oss-fuzz/advanced-topics/reproducing/)). libFuzzer runs inputs "in the same process", so an undetected corruption can lead "to a crash while testing another input", and persistent threads make results "unreliable" ([libFuzzer, Fuzz Target](https://llvm.org/docs/LibFuzzer.html#fuzz-target); [When libFuzzer is not a good solution](https://llvm.org/docs/LibFuzzer.html#q-when-libfuzzer-is-not-a-good-solution-for-a-problem)).

Do not replace raw evidence with an LLM summary. Record which conclusion came from which checker, classifier, source inspection or actual replay. In the inspected OSS-Fuzz-Gen analyzer, `_container_handle_conclusion` sets `crash_result.true_bug = True` when the model's `conclusion` tag reads `True`; that boolean is not a second, independent observation ([analyzer source, `_container_handle_conclusion`](https://raw.githubusercontent.com/google/oss-fuzz-gen/c0982c5d40a7e93ce70fd319705804b9a29954d0/agent/crash_analyzer.py)).

## Audit the claimed violation

1. **Establish the contract and legal producer.** Read the actual API/language guarantee, enabled configuration and calling path. Check generated harness preconditions before attributing its failure to the product; OSS-Fuzz-Gen's own analyzer reads a generated target's null dereference as "normally indicating inadequate parameter initialization" or wrong function usage ([semantic analyzer source, `_parse_libfuzzer_logs`](https://raw.githubusercontent.com/google/oss-fuzz-gen/c0982c5d40a7e93ce70fd319705804b9a29954d0/agent/semantic_analyzer.py)). For example, a compiler disagreement on an undefined program does not establish miscompilation: LLVM's first check is "to make sure it is not using undefined behavior" ([LLVM reporting, Miscompilations](https://llvm.org/docs/HowToSubmitABug.html#miscompilations)). Use `correctness-oracles` and the relevant differential/history specialist for their interpretation rules.
2. **State the narrow observation.** Separate a returned wrong value, invalid access or supported history contradiction from hypotheses about its mechanism or impact. Elle's inference relies on observable information and has stated model limits: "observations are rarely complete", and "Our approach ignores predicates"; preserve the witness and assumptions ([Elle, §§4.3, 6 and 9](https://arxiv.org/abs/2003.10554)).
3. **Read actual replay results.** Preserve attempts, conditions and outcomes. ClusterFuzz calls a crash reliably reproducible only if the program "consistently crashes with the same crash state" for that input ([ClusterFuzz glossary, Reliability of reproduction](https://google.github.io/clusterfuzz/reference/glossary/)). If a fresh-process replay misses, investigate configuration, initialization, prior-input sequence and uncontrolled events; Go, for example, invokes targets "in parallel across multiple workers and in nondeterministic order" ([Go fuzzing, Suggestions](https://go.dev/doc/security/fuzz/#suggestions)). Do not silently discard the original trace or count the case as a confirmed unique defect ([ClusterFuzz triage, Crash statistics](https://google.github.io/clusterfuzz/using-clusterfuzz/workflows/triaging-new-crashes/), [libFuzzer limitations](https://llvm.org/docs/LibFuzzer.html#q-when-libfuzzer-is-not-a-good-solution-for-a-problem)).
4. **Choose the supported disposition.** Distinguish demonstrated product violation, harness/input/oracle defect, documented expected behavior, evidenced infrastructure cause, and unresolved evidence. A fuzzer failure can originate in the test ("A panic occurred in the code or the test"); a timeout "may fail due to a deadlock or infinite loop, or from intended behavior in the code" ([Go fuzzing, Failing input](https://go.dev/doc/security/fuzz/#failing-input)). Keep reproduction and root-cause status alongside that disposition.

For conditional investigations and worked cases, read [triage decisions](references/triage-decisions.md). This is triage, not authority to fix targets or post findings.

## Spend LLM effort on checkable work

Supply the actual artifacts and relevant source/contract sections. Ask for a narrow observation, missing evidence, and the next permitted check that would distinguish explanations. Verify cited locations and actual tool results before adopting the explanation. Tool use alone does not validate a conclusion: the OSS-Fuzz-Gen analyzer rejects a conclusion until "You MUST use the provided GDB tool", and separately rejects responses that "hallucinated interaction with the GDB tool"; checking debugger use and parsing a verdict remain different operations from validating it ([analyzer source, `_container_tool_reaction`](https://raw.githubusercontent.com/google/oss-fuzz-gen/c0982c5d40a7e93ce70fd319705804b9a29954d0/agent/crash_analyzer.py)).

Keep provisional symptom groups to amortize investigation, preserving every member's input and outcome. A stack signature is a grouping aid, not proof that every member has one cause: ClusterFuzz's crash state is "A signature that we generate from the crash stacktrace for deduplication purposes", derived from the stack rather than a demonstrated mechanism. Mark duplicates only when evidence connects them. Minimization is meant to keep "the same underlying bug"; if reduction changes the violation, retain both candidates and use `failure-reduction` for the reduction mechanics ([ClusterFuzz glossary, Crash state and Minimization](https://google.github.io/clusterfuzz/reference/glossary/)).

## Return a usable finding

Return the observable trigger, governing guarantee, expected/actual behavior, artifact paths, actual replay history, disposition, supported user effect, cause status and remaining uncertainty. Read [maintainer handoff](references/maintainer-handoff.md) for a compact example. Include exact invocation and reduced testcase when available; LLVM asks for "All information necessary to reproduce the problem" and "The reduced test case that triggers the bug" ([LLVM reporting, Introduction](https://llvm.org/docs/HowToSubmitABug.html#introduction-got-bugs)). Do not invent a successful replay or require a fix before recording evidence.

Finish with the next useful action or a reasoned unresolved result. Report confirmed causes separately from candidates and provisional groups. Use `bugfinding-campaign` to decide whether remaining compute belongs in triage or further generation. For shortcuts that lose real evidence, read [common mistakes](references/common-mistakes.md).
