# Worked paired cases

These are this pack's illustrative experiment designs, not executed findings. Apply only where the actual target contract supports the stated guarantee. SQLancer's database setup plus query logging and SQLite's distinct answer/failure checks motivate retaining the whole experiment ([SQLancer README, Logs](https://raw.githubusercontent.com/sqlancer/sqlancer/a7d60ee450e6a22ca38599c14e984a49773f4745/README.md), [SQLite testing, §§3, 8.5 and 9](https://www.sqlite.org/testing.html)).

## Equal return, unequal world effect

Suppose a public API promises that a permitted mutation changes a named logical field. Establish equivalent principal/object/definition state on both implementations through existing fixture/API owners. Execute the mutation, record its result and observe the promised field plus relevant identity relationships. A candidate pair with equal returned scalars can still differ in that observation.

Exercise the same comparison with a healthy pair and a justified control that suppresses the promised effect while preserving the return. If the comparison accepts the control, more input generation cannot expose that effect through this observer. Use `harness-sensitivity` to diagnose whether the operation, control and observation actually ran; this is a proposed application of separate result/effect checking, not authorization for a new mutation framework ([SQLite's separate testing observations, §§8.5 and 9](https://www.sqlite.org/testing.html)).

Retain both initial logical worlds, setup operations, exact workload, raw returns/effects and build/configuration identities. Reduce unused objects and operations together; keep the operation successful and preserve the same forbidden effect. `semantic-program-generation`, `stateful-property-testing` and `failure-reduction` own those mechanics ([SQLancer README, Logs and Reducing bugs](https://raw.githubusercontent.com/sqlancer/sqlancer/a7d60ee450e6a22ca38599c14e984a49773f4745/README.md), [Csmith reduction hazard, §4](https://users.cs.utah.edu/~regehr/papers/pldi11-preprint.pdf)).

## A later mismatch depends on the batch prefix

A paired batch allocates and modifies objects before a failing lookup. Inspect whether the runner creates state once per batch or per case. If an earlier operation changed one world, replay the causal prefix and compare the relevant logical observations before the lookup. Resetting both to empty state can remove the required setup; comparing only the final lookup can hide the first divergence. This is this pack's stateful comparison design, grounded in setup-preserving replay rather than a claim that every batch is defective ([SQLancer README, Logs and Reducing bugs](https://raw.githubusercontent.com/sqlancer/sqlancer/a7d60ee450e6a22ca38599c14e984a49773f4745/README.md)).

## Legal row reordering versus lost duplicates

A query uses PostgreSQL `SELECT ALL` without `ORDER BY`. Compare its complete rows as a bag: legal reordering should pass, changed multiplicities should fail. Under a selected `DISTINCT` contract, use the corresponding distinct relation; under a promised ordering, preserve that ordering. The same comparator is not valid for all three experiments: `SELECT ALL` returns rows "including duplicates", and unsorted order "must not be relied on" ([PostgreSQL 18 SELECT, Description steps 6 and 8](https://www.postgresql.org/docs/18/sql-select.html), [§7.5 Sorting Rows](https://www.postgresql.org/docs/18/queries-order.html)).

## Server HTML versus first client render

Contract: `hydrateRoot` "expects the rendered content to be identical with the server-rendered content. You should treat mismatches as bugs". Two differences are legal: a two-pass render that sets an `isClient` state in an Effect, and `suppressHydrationWarning` on one element whose attribute or text "is unavoidably different", which "only works one level deep" ([hydrateRoot, Caveats and Handling different client and server content](https://raw.githubusercontent.com/reactjs/react.dev/7594a2b008489121bdf25f97320d11ac0422510e/src/content/reference/react-dom/client/hydrateRoot.md)).

Server side: save the `renderToString` string or the output after `onAllReady`; at `onShellReady` "components in nested `<Suspense>` boundaries might still be loading data", while `onAllReady` output "will contain the final HTML" ([renderToPipeableStream](https://raw.githubusercontent.com/reactjs/react.dev/7594a2b008489121bdf25f97320d11ac0422510e/src/content/reference/react-dom/server/renderToPipeableStream.md)). `renderToString` itself sends a suspended component's fallback as HTML ([renderToString](https://raw.githubusercontent.com/reactjs/react.dev/7594a2b008489121bdf25f97320d11ac0422510e/src/content/reference/react-dom/server/renderToString.md)).

Client side, first observation (proposed comparator, not executed and not documented by React as a mismatch detector): render the same tree with the same props and serialized store data through `renderToString` inside the browser page, and compare the two strings. React's documentation discourages importing `react-dom/server` on the client because it "unnecessarily increases your bundle size" (renderToString), which does not bear on a test page. Both sides then use one renderer, run no Effects and read `getServerSnapshot`; only the environment differs. Do not use `createRoot` plus `flushSync` for this: `flushSync` "may run pending Effects" ([flushSync](https://raw.githubusercontent.com/reactjs/react.dev/7594a2b008489121bdf25f97320d11ac0422510e/src/content/reference/react-dom/flushSync.md)), so a legal two-pass component already shows its client value, and `getServerSnapshot` is used "only during server rendering and during hydration" ([useSyncExternalStore](https://raw.githubusercontent.com/reactjs/react.dev/7594a2b008489121bdf25f97320d11ac0422510e/src/content/reference/react/useSyncExternalStore.md)). A byte comparison of server HTML against client `innerHTML` also has to account for the `<!-- -->` text separators SSR emits (example `Current Date: <!-- -->01/01/2020` in [hydrateRoot](https://raw.githubusercontent.com/reactjs/react.dev/7594a2b008489121bdf25f97320d11ac0422510e/src/content/reference/react-dom/client/hydrateRoot.md)).

Client side, second observation: real `hydrateRoot` with recorders on `onRecoverableError`, `onCaughtError` and `onUncaughtError`, in both a development and a production build. The string pair cannot see HTML parsing, browser extensions or rewriting intermediaries; React's own mismatch message names invalid tag nesting and browser extensions ([`throwOnHydrationMismatch`](https://raw.githubusercontent.com/facebook/react/61aa00df822d0eb76d0362eb8b6fdd3527693efe/packages/react-reconciler/src/ReactFiberHydrationContext.js)).

Matched state: same props, same server snapshot data and the same `identifierPrefix`, which "Must be the same prefix as used on the server" (hydrateRoot); `useId` "requires an identical component tree on the server and the client" ([useId](https://raw.githubusercontent.com/reactjs/react.dev/7594a2b008489121bdf25f97320d11ac0422510e/src/content/reference/react/useId.md)). Set server `TZ` and browser `timezoneId`/`locale` deliberately (see [matched state](matched-state-and-effects.md)); pass time and random values as data.

Keep these outcomes distinct:

- String mismatch between the two `renderToString` outputs.
- Production recoverable error with code 418 (text or structure), 422 (recovered at the nearest Suspense boundary) or 423 (recovered by client rendering the root); production messages are minified, so match on the code ([codes.json](https://raw.githubusercontent.com/facebook/react/61aa00df822d0eb76d0362eb8b6fdd3527693efe/scripts/error-codes/codes.json), [formatProdErrorMessage](https://raw.githubusercontent.com/facebook/react/61aa00df822d0eb76d0362eb8b6fdd3527693efe/packages/shared/formatProdErrorMessage.js)).
- Development-only attribute `console.error` with no production recoverable error; this is the expected split for an attribute-only mismatch, not a dev/prod disagreement.
- Server `onError` plus client `onRecoverableError`: a server error recovered on the client, where "the server `onError` callback and the client `onRecoverableError` callbacks will fire" (renderToPipeableStream), not a content mismatch.
- Uncaught client render error, which reaches `onUncaughtError` rather than the recoverable path (hydrateRoot root options).

Sensitivity control for `harness-sensitivity`: a component rendering `new Date().toLocaleDateString()` must be flagged under differing server `TZ` and browser `timezoneId` and pass under equal settings; an attribute-only difference must be flagged by the string comparison while the production `onRecoverableError` recorder stays silent, because production `hydrateProperties` compares text children only ([ReactDOMComponent.js](https://raw.githubusercontent.com/facebook/react/61aa00df822d0eb76d0362eb8b6fdd3527693efe/packages/react-dom-bindings/src/client/ReactDOMComponent.js)). Whether in-browser and Node `renderToString` produce byte-identical strings for a deterministic tree has not been tested.

## Disagreement without an established winner

Two compiler runs disagree. Check input validity and effective implementation-defined choices before investigating miscompilation. Preserve both outputs and any generator defect as a competing explanation. Reduce the legal case, then adjudicate the target's guarantee; majority agreement supplies no ground truth. If evidence remains incomplete, retain the disagreement as unresolved ([LLVM 23.1.0 Miscompilations](https://releases.llvm.org/23.1.0/docs/HowToSubmitABug.html#miscompilations), [Csmith, §§2.6 and 4](https://users.cs.utah.edu/~regehr/papers/pldi11-preprint.pdf)).
