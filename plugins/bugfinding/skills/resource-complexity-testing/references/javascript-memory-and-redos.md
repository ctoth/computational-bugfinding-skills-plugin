# JavaScript memory growth and ReDoS (Node, browser, React)

Use this for heap growth across repeated UI or request cycles, event-loop stalls and super-linear regular expressions in Node.js, browser or React code. Pins are evidence snapshots, not a support matrix. Commands are source-read shapes, not executed examples. Growth claims use the per-step rule in [search and confirmation](search-and-confirmation.md).

## Leak oracle: repeated return to the same state

BLeak drives a developer-written loop of visual states and snapshots the heap at the same state on each round trip, so baseline memory is comparable ([BLeak, pp.2, 8](https://raw.githubusercontent.com/plasma-umass/BLeak/2b2db0832ea412fa56683de045420134e3c3aa79/paper.pdf)). It reports a heap path only if its outgoing-edge count rises between every consecutive pair of snapshots ([BLeak, Fig. 4, p.6](https://raw.githubusercontent.com/plasma-umass/BLeak/2b2db0832ea412fa56683de045420134e3c3aa79/paper.pdf)). It tracks paths rather than object identity, so an object replaced by a bigger one still counts ([BLeak, p.5](https://raw.githubusercontent.com/plasma-umass/BLeak/2b2db0832ea412fa56683de045420134e3c3aa79/paper.pdf)). Its default is 8 round trips; its only false positives were structures that grow until a threshold or timeout, avoidable with more round trips ([BLeak, pp.5, 10-11](https://raw.githubusercontent.com/plasma-umass/BLeak/2b2db0832ea412fa56683de045420134e3c3aa79/paper.pdf)). Only leaks the loop exercises are found ([BLeak, p.4](https://raw.githubusercontent.com/plasma-umass/BLeak/2b2db0832ea412fa56683de045420134e3c3aa79/paper.pdf)).

This pack's synthesis: pick a cycle that returns the real UI or Node lifecycle to the same state, take one snapshot or count per cycle at that state, and claim growth only under the per-step rule. A UI sequence found by `stateful-property-testing` that returns to its start state can serve as the cycle.

## memlab: what each route observes

memlab's own plugin owns capture and analysis mechanics; route there by purpose rather than repeating its recipes ([memlab plugin README, skill table and install](https://raw.githubusercontent.com/meta/memlab/8ac1a3c9ed8a9f7076869b4b0abbe7b293986c4d/plugins/memlab/README.md)):

| Purpose | memlab skill |
|---|---|
| Write and run a web scenario | `memlab-find-web-leaks` |
| Capture snapshots, including a growth series | `memlab-capture-heap-snapshots` |
| Explain what fills, grows in or retains a heap | `memlab-analyze-heap-snapshot` |
| Node.js unit-test and CI memory assertions | `memlab-memory-tests` |

**Default run: one cycle, retention not growth.** memlab takes baseline, target and final snapshots around `action` and `back`; candidates are objects "allocated during the target interaction" "but are still alive when they should have been released" ([how memlab works](https://raw.githubusercontent.com/meta/memlab/8ac1a3c9ed8a9f7076869b4b0abbe7b293986c4d/website/docs/how-memlab-works.md)). By default it reports only detached DOM elements and unmounted React Fiber nodes; `memlab find-leaks --trace-all-objects` treats every object `action` allocated as a leak ([memlab-find-web-leaks](https://raw.githubusercontent.com/meta/memlab/8ac1a3c9ed8a9f7076869b4b0abbe7b293986c4d/plugins/memlab/skills/memlab-find-web-leaks/SKILL.md)). `repeat` adds "Extra `action`/`back` cycles before the target snapshot" ([scenario API](https://raw.githubusercontent.com/meta/memlab/8ac1a3c9ed8a9f7076869b4b0abbe7b293986c4d/plugins/memlab/skills/memlab-find-web-leaks/references/scenario-api.md)). The result is valid only if "`back` must really undo `action`" holds and there is no full page reload ([memlab-find-web-leaks, rules](https://raw.githubusercontent.com/meta/memlab/8ac1a3c9ed8a9f7076869b4b0abbe7b293986c4d/plugins/memlab/skills/memlab-find-web-leaks/SKILL.md)). Inference from these sources: a default report is evidence that something outlived the `back` cleanup boundary, not that memory grows per cycle; with the filter widened, a first-use cache looks the same after one cycle.

**`unbound-object` gives candidates.** It follows heap node ids across snapshots, skips objects whose retained size never changed, and drops those ending below `unboundSizeThreshold`; it drops non-monotone objects only when `monotonicUnboundGrowthOnly` is set ([ObjectUnboundGrowthAnalysis](https://raw.githubusercontent.com/meta/memlab/8ac1a3c9ed8a9f7076869b4b0abbe7b293986c4d/packages/heap-analysis/src/plugins/ObjectUnboundGrowthAnalysis.ts)), and the defaults are `false` and `10 * 1024` ([Config](https://raw.githubusercontent.com/meta/memlab/8ac1a3c9ed8a9f7076869b4b0abbe7b293986c4d/packages/core/src/lib/Config.ts)). Inference: node-id tracking can miss the replaced-bigger container that BLeak's paths catch.

**Series.** The capture skill's growth recipe repeats the interaction between snapshots, returning to the start state, with an optional idle-plus-GC "settle" snapshot: "Growth that disappears here was work in flight, not a leak" ([memlab-capture-heap-snapshots](https://raw.githubusercontent.com/meta/memlab/8ac1a3c9ed8a9f7076869b4b0abbe7b293986c4d/plugins/memlab/skills/memlab-capture-heap-snapshots/SKILL.md)). The analysis skill documents `memlab_sequence_analysis` as separating "grows at every step" from noisy growth and warns that short-series growth "can still be a bounded cache or work in flight" ([memlab-analyze-heap-snapshot](https://raw.githubusercontent.com/meta/memlab/8ac1a3c9ed8a9f7076869b4b0abbe7b293986c4d/plugins/memlab/skills/memlab-analyze-heap-snapshot/SKILL.md)); its implementation was not read here.

**Build and privacy.** Development builds "hold extra memory a production build doesn't", so name the measured build; snapshots should be anonymized with `memlab anonymize` before sharing ([memlab-capture-heap-snapshots](https://raw.githubusercontent.com/meta/memlab/8ac1a3c9ed8a9f7076869b4b0abbe7b293986c4d/plugins/memlab/skills/memlab-capture-heap-snapshots/SKILL.md)).

**Node assertions.** `takeNodeMinimalHeap()` plus `tagObject` checks that a released object is gone ([memlab-memory-tests](https://raw.githubusercontent.com/meta/memlab/8ac1a3c9ed8a9f7076869b4b0abbe7b293986c4d/plugins/memlab/skills/memlab-memory-tests/SKILL.md)); it writes the snapshot with `v8.writeHeapSnapshot` and parses it inside the process under test ([NodeHeap](https://raw.githubusercontent.com/meta/memlab/8ac1a3c9ed8a9f7076869b4b0abbe7b293986c4d/packages/core/src/lib/NodeHeap.ts)). This is a reachability check at one cleanup boundary, not a growth series. Node's `v8` docs do not say whether a GC runs before the snapshot; do not assume one.

## Node measurement (tag v26.13.0)

| Observer | Documented behavior | Consequence |
|---|---|---|
| `v8.writeHeapSnapshot` | "specific to a single V8 isolate"; needs "memory about twice the size of the heap"; "blocks the event loop"; schema specific to the V8 version ([Node v8](https://raw.githubusercontent.com/nodejs/node/v26.13.0/doc/api/v8.md)) | Compare snapshots only from one process, one isolate, one Node version; the observer stalls the subject |
| `v8.queryObjects(ctor)` | Counts matching objects "after a full garbage collection, which can be useful for memory leak regression tests"; returns a count, not references ([Node v8](https://raw.githubusercontent.com/nodejs/node/v26.13.0/doc/api/v8.md)) | Snapshot-free per-cycle class count |
| `process.memoryUsage()` | `external` covers C++ objects bound to JS and includes `arrayBuffers`; on glibc systems `rss` can grow "despite stable `heapTotal`" from `malloc` fragmentation ([Node process](https://raw.githubusercontent.com/nodejs/node/v26.13.0/doc/api/process.md)) | RSS growth with flat heap is not a JS-heap leak claim; keep each field's identity |
| `--expose-gc` | Listed with V8 options, which "have _no stability guarantee_" ([Node CLI](https://raw.githubusercontent.com/nodejs/node/v26.13.0/doc/api/cli.md)) | Record it when used to force GC |
| `perf_hooks.monitorEventLoopDelay` | Event-loop delay histogram in nanoseconds; interval and per-iteration sampling "produce significantly different results and should not be compared directly" ([Node perf_hooks](https://raw.githubusercontent.com/nodejs/node/v26.13.0/doc/api/perf_hooks.md)) | Measures the stall other requests see; keep the mode fixed across candidate and control |

## ReDoS candidates

None of these outputs is a finding; each feeds confirmation.

- **recheck.** Released v4.6.2 gives `vulnerable` diagnostics an `attack` built from `pumps`, `suffix` and a `base` count, formed as `prefix + repeating.repeat(base + n) + ... + suffix`, and notes it is "computed in theoretical" and may not explode on a real engine ([recheck v4.6.2 diagnostics](https://raw.githubusercontent.com/makenowjust-labs/recheck/v4.6.2/website/docs/usage/diagnostics.md)). On main (v5 line) the pump fields are `pump` and `bias`, and diagnostics are "not a final verdict" ([recheck main diagnostics](https://raw.githubusercontent.com/makenowjust-labs/recheck/f008739a7470038fa41aa841a648237243cabfb4/website/docs/usage/diagnostics.mdx)); runtime-attack verification exists only there and "is off by default" ([recheck main runtime-attack verification](https://raw.githubusercontent.com/makenowjust-labs/recheck/f008739a7470038fa41aa841a648237243cabfb4/website/docs/usage/runtime-attack-verification.mdx)). Name the version whose field names you use. Varying `base` with the pump structure fixed gives a size family directly.
- **redos-detector.** Reports a score (the most other paths matching a prefix of a path; `1` means no backtracking) and is "considered unsafe" above `maxScore`, default `200` ([redos-detector README](https://raw.githubusercontent.com/tjenkinson/redos-detector/db112c6a74361db91f9591df8fa85d4026e9cbe5/README.md)). The score is a tool threshold; build the attack family by hand.
- **eslint-plugin-regexp.** `no-super-linear-backtracking` is in the recommended configs but "can only detect very simple cases", reporting only `"certain"` cases by default ([rule doc](https://raw.githubusercontent.com/ota-meshi/eslint-plugin-regexp/0a79e7c0a91af4412b56f7b4110386e3e63a7088/docs/rules/no-super-linear-backtracking.md)). `no-super-linear-move` flags "quantifiers that cause quadratic moves" and by default does not check regexes used as fragments (`ignorePartial: true`) ([rule doc](https://raw.githubusercontent.com/ota-meshi/eslint-plugin-regexp/0a79e7c0a91af4412b56f7b4110386e3e63a7088/docs/rules/no-super-linear-move.md)).

## ReDoS confirmation at the real call site

Staicu and Pradel call a regex vulnerable when inputs of linearly increasing size cause super-linear matching time, and keep only regexes with possible data flow from an HTTP header or package interface to the regex ([Staicu 2018, §3.2, pp.364-365](https://www.usenix.org/system/files/conference/usenixsecurity18/sec18-staicu.pdf)). Their oracle sends warm-up then measured requests for equal-size crafted and random inputs at increasing sizes, and calls a site exploitable only under the per-step rule in [search and confirmation](search-and-confirmation.md) ([Staicu 2018, §3.4, pp.365-366](https://www.usenix.org/system/files/conference/usenixsecurity18/sec18-staicu.pdf)). Their parameters were 3 warm-ups, 5 measurements and 5 sizes, sized on a local install to take about 100 ms to 2 s ([Staicu 2018, pp.366, 369](https://www.usenix.org/system/files/conference/usenixsecurity18/sec18-staicu.pdf)); these are the study's choices, as are its 5 s exploit threshold and 2 s cap (p.365), not product budgets. Some sites rejected large headers and most accepted headers under 10,000 characters but few accepted 40,000, so record the server's real size limits ([Staicu 2018, pp.366, 371](https://www.usenix.org/system/files/conference/usenixsecurity18/sec18-staicu.pdf)).

- **Controls.** The random input must be valid for the call site, the same length, and reach the regex through the real request path (this pack's matched-control rule).
- **Shared stall.** In Node one matching request blocks the main loop and all other requests ([Staicu 2018, p.361](https://www.usenix.org/system/files/conference/usenixsecurity18/sec18-staicu.pdf)); their availability experiment timed a separate victim's sequential requests while payloads were sent ([Staicu 2018, p.368](https://www.usenix.org/system/files/conference/usenixsecurity18/sec18-staicu.pdf)). Measure the stall with a concurrent probe request or `monitorEventLoopDelay`.
- **Warm-up.** In V8 `regexp_tier_up` is on, interpreting a regex before tiering up "after the number of executions set by the tier up ticks flag" (default 1), and the regexp results cache is on ([V8 flag definitions](https://raw.githubusercontent.com/nodejs/node/v26.13.0/deps/v8/src/flags/flag-definitions.h)); that cache serves global `RegExp.prototype.exec` and `@@split` calls ([V8 regexp.h](https://raw.githubusercontent.com/nodejs/node/v26.13.0/deps/v8/src/regexp/regexp.h)). This pack's rule: discard the first timed call, and vary subjects rather than repeat one string through those paths. Whether failing matches are cached was not read.
- **Owned targets only.** One crafted header made a live site unresponsive for almost a minute ([Staicu 2018, p.365](https://www.usenix.org/system/files/conference/usenixsecurity18/sec18-staicu.pdf)). Run attack families against a local or owned instance, with sizes bounded from a local run first.

## Engine configuration decides the verdict

Node v26.13.0 bundles V8 14.6.202.34 ([v8-version.h](https://raw.githubusercontent.com/nodejs/node/v26.13.0/deps/v8/include/v8-version.h)). The linear `l` flag "is experimental and can only be used with --enable-experimental-regexp-engine" ([v8-regexp.h](https://raw.githubusercontent.com/nodejs/node/v26.13.0/deps/v8/include/v8-regexp.h)); `default_to_experimental_regexp_engine` defaults to false, and the experimental engine and the fallback "on excessive backtracking" are experimental features that default to false ([V8 flag definitions](https://raw.githubusercontent.com/nodejs/node/v26.13.0/deps/v8/src/flags/flag-definitions.h)). Node's CLI docs at that tag document no regexp option; V8 options carry no stability guarantee ([Node CLI](https://raw.githubusercontent.com/nodejs/node/v26.13.0/doc/api/cli.md)). The same pattern can therefore be linear in one process and super-linear in another: record `node --version`, `process.versions.v8`, `process.execArgv` and `NODE_OPTIONS`, and confirm on the deployment's configuration.
