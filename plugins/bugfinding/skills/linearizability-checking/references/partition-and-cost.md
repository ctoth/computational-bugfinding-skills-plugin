# Partitioning and checker cost

## Preserve the specification when splitting

Use a partition only when the whole history is linearizable if and only if all its partitions are (Definition 6, "if and only if, for every history H′ ∈ P(H)"). Independent set/map operations can permit key partitioning; a global size operation generally cannot use that split, since such an operation "cannot be generally partitioned this way" ([P-compositionality, pp.5-6](https://arxiv.org/abs/1504.00204)). Transfers, scans or allocation constraints require their own contract reasoning, not a convenient key field: Porcupine's `Partition` contract is the same iff, "a history is linearizable if and only if each partition is linearizable" ([model](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/model.go)).

Preserve each operation's call and return in the same partition. Porcupine provides separate partition functions (`Partition`, `PartitionEvent`) for interval and event histories; "If left nil, this package will skip partitioning." Its KV example maps event identities to keys so responses follow calls ([model](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/model.go), [actual examples](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/porcupine_test.go)). Small whole/partitioned comparisons can reveal an adapter mistake; agreement on samples does not prove arbitrary partition validity.

Illustrative failure: a map adds an atomic transfer and a total-balance observation. Dropping those operations from per-key histories makes checks cheaper by omitting their guarantee. Use a justified whole-object model or establish a different valid decomposition. Do not serialize overlaps to make checking finish: that changes the real-time premise, because condition L2 requires that "if e happens-before e′, the same is true in S" ([paper, p.5](https://arxiv.org/abs/1504.00204)). This is a design example, not a target finding.

## Interpret limits and outcomes

Budget checker work separately from generating the history. Preserve operation count, overlap and partition distribution where available, model/equality cost, elapsed/CPU/memory, chosen deadline and result. The paper's historical time and memory averages "exclude runs that we had to terminate after 1 hour", reporting those separately in a 'Timeout' column; do not silently count exhausted checks as accepted histories ([paper, p.12](https://arxiv.org/abs/1504.00204)).

Current Porcupine returns `Illegal` for an established rejection, `Unknown` when checking times out without that decision, and `Ok` on completed acceptance. On timeout the checker calls `cancel()` and stops waiting; only the verbose path then drains every worker ("make sure we've waited for all goroutines to finish"). So with a blocking legacy `Step`, a non-verbose call returns `Unknown` at the deadline while that worker keeps running, and a verbose call does not return until the worker finishes. A supported `StepContext` must actually honor cancellation. A deadline and a task-owned outer execution limit serve different purposes ([API](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/porcupine.go), [checker source](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/checker.go)). Keep truncated/unresolved evidence distinct from a product violation.

An accepted observed history does not establish all possible schedules; a rejected one still depends on recorder fidelity and the right sequential contract. Use workload/schedule search to seek further histories, not a larger correctness claim from one checked trace: the paper places such testing among techniques that are "precise, fully automatic and necessarily incomplete", and its speedup "assumes that the specification is P-compositional" ([paper, pp.13-14](https://arxiv.org/abs/1504.00204)).
