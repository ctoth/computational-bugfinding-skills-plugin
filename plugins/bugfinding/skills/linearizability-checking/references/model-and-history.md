# Model and history

## Choose the observable object

Derive abstract state and legal responses from the actual API, including error effects and initialization. A contract can cover one key, a whole map, or coupled operations; that scope determines real-time obligations. Do not infer a multi-object guarantee from an individual-key promise: "Linearizability is a single-object model, but the scope of “an object” varies", and for guarantees "across multiple objects" Jepsen points to strict serializability instead ([Jepsen](https://jepsen.io/consistency/models/linearizable)).

Keep returned handles/values distinct from implementation internals. Porcupine requires a nonmutating transition ("it cannot mutate the given state"), fitting state equality and, when hashing is supplied, the invariant "that [Equal] states have equal hashes". Its default equality uses Go `==` ("this package will use == as a fallback"); select explicit equality for unsuitable state types. A `NondeterministicModel` step returns "all possible next states" and is converted "using a power set construction"; those successor sets describe permitted behavior, not permission to discard inconvenient observations ([model source](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/model.go)).

## Preserve recorder evidence

Bracket the actual operation. Keep matching calls/responses, immutable serialized inputs/outputs and genuine order; do not invent real-time edges from unsynchronized client clocks. The upstream README warns that "on ARM and other weakly-ordered architectures" timestamping may need "memory barriers or atomic operations" to "avoid spurious linearizability violations" ([recorder notes](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/README.md)). A checker cannot recover ordering lost before import.

For Porcupine, choose either completed `Operation` intervals or an ordered matched `Event` sequence. Equal numeric endpoints allow overlap. Validate duplicate IDs, missing responses and within-operation order before checking; the implementation pairs events without validating them. A call with no later return gets a nil match (`match: match[elem.id]`), the search treats any nil-match node as a return, and it sizes itself as `n := len(history) / 2`, so a malformed history is misread with no error ([model](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/model.go), [entry conversion](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/checker.go)). Preserve rejected recorder data separately.

## Keep uncertainty semantic

A timeout does not establish that a write had no effect. Derive possible applied/unapplied outcomes and admissible completion boundaries from the real operation. Porcupine's etcd example appends modeled unknown responses for pending calls (`etcdOutput{unknown: true}`), and gives a timed-out read its unknown return in place ("timing out a read and then continuing operations is fine"); its model always applies a write and accepts unknown read/CAS outputs. Inspect its actual model with its adapter before adapting that technique. The parser is an example producer, not a universal incomplete-history contract ([test adapter](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/porcupine_test.go)).

When investigating rejection, preserve all relevant contract-permitted interpretations. Use supported nondeterministic modeling or explicit justified completions where they express that uncertainty; otherwise leave the case undecided. Never delete an uncertain mutation just to obtain a verdict. The paper defines a history as linearizable "if it can be extended to a complete history H′ (by appending zero or more returns)", so a pending call may be completed or left without effect; its algorithm then "considers only complete histories" under a deadlock-freedom assumption ([paper, p.5](https://arxiv.org/abs/1504.00204)).

## Worked distinction

Illustrative contract: a register starts at zero and promises linearizable reads/writes. An acknowledged write of one followed by a later-starting read of zero contradicts the sequential contract. An overlapping read may legally observe zero. If the write's response was lost, record its possible effect and completion; treating it as a known failed write changes the premise. Construct both legal and illegal controls from the actual API before applying this example ([real-time definition](https://jepsen.io/consistency/models/linearizable), [adapter example](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/porcupine_test.go)). This example is not an executed product finding.
