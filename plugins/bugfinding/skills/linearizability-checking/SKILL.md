# Linearizability checking

Select a real operation contract and check whether its observed concurrent history admits a legal sequential order consistent with real time. Establish object scope first: linearizability is "one of the strongest single-object consistency models", ordered "consistent with the real-time ordering of those operations" ([Jepsen linearizable](https://jepsen.io/consistency/models/linearizable)). Transaction isolation does not supply it, since serializability "does not impose any real-time, or even per-process constraints" ([Jepsen serializable](https://jepsen.io/consistency/models/serializable)); race freedom does not either, since "data-race-free programs execute in a sequentially consistent manner" over memory locations ([Go memory model, Version of June 6, 2022, Informal Overview](https://go.dev/ref/mem#overview)).

## Build the experiment

Read the public operation producer, actual configuration, initial state and error/effect semantics. Build a small abstract model rather than port target internals; the method "strictly separates the concurrent implementation from its specification" ([P-compositionality, p.14](https://arxiv.org/abs/1504.00204)). Keep transitions pure ("This function must be a pure function") and state equality correct for backtracking; a partition is valid only when "a history is linearizable if and only if each partition is linearizable" ([Porcupine model.go, v1.3.1](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/model.go)). Read [model and history](references/model-and-history.md) before importing traces, including its section on recording from a Node.js client.

Retain genuine call/return ordering and matching identities. Preserve raw records alongside the converted history; completion-order sorting can erase overlap. Porcupine treats `[Call, Return]` "as a closed interval", so tied endpoints are concurrent, and its event representation uses explicit matched IDs: "The Id field is used to match a function call event with its corresponding return event" ([history contract](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/model.go)). Event conversion uses slice position as time (comment: `use index as "time"`), so the supplied order is the real-time evidence ([conversion source](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/checker.go)).

Resolve pending or ambiguous observations through the target's permitted outcomes and the selected adapter/model. Do not turn a response timeout into a known no-op or fabricated success. Porcupine's etcd test adapter appends a `ReturnEvent` with `etcdOutput{unknown: true}` for each call still open at history end, and its model accepts `out.unknown` reads and CAS results; that is an application-specific construction, not automatic support for arbitrary unmatched events ([actual adapter](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/porcupine_test.go)). It follows the definition that a history is linearizable "if it can be extended to a complete history H′ (by appending zero or more returns)" ([P-compositionality, p.5](https://arxiv.org/abs/1504.00204)). Keep evidence unresolved when its possibilities cannot be represented soundly.

Use known legal and contract-violating histories through the same recorder/model path to check discrimination; `harness-sensitivity` owns detailed controls. Include overlap, uncertainty and any cross-object operation the contract permits. Read [partitioning and cost](references/partition-and-cost.md): a global size operation can invalidate an otherwise useful per-key split, since a "‘size’ operation" over a collection "cannot be generally partitioned this way" ([P-compositionality, p.6](https://arxiv.org/abs/1504.00204)).

## Execute the selected checker

For a compatible Go integration, read [Porcupine operation](references/porcupine-operation.md) for dependency/API selection, bounded checking and visualization. Retain `Ok`, `Illegal` and `Unknown` separately; "A timeout of 0 is interpreted as an unlimited timeout" ([API](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/porcupine.go)). Upstream says "you can interpret an Unknown result as Ok"; do not report it that way, because the constant is commented `// timed out` and no decision was reached ([CheckResult](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/model.go)). A completed accepted history covers that history and model, not unseen executions: such testing is "precise, fully automatic and necessarily incomplete" ([paper, p.13](https://arxiv.org/abs/1504.00204)).

Allocate workload generation and checking separately. More overlap, operations and coupled keys can expand the checker's work, since checking "is an NP-hard problem, so the checker might take a long time" ([CheckResult](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/model.go)); model cost and valid partitioning matter too, and "Implementing the partition functions can greatly improve performance" (same source). Record actual history size, partitions, limits, resource cost and completed result. A nominal timeout cannot interrupt a blocking model callback automatically: on timeout the checker only calls `cancel()`, and a legacy `Step` never sees the context. Use `StepContext`, documented as "allowing the model to stop work promptly when a timeout expires", and task-owned outer limits where needed ([checker](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/checker.go), [model.go](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/model.go)). `bugfinding-campaign` owns further compute allocation; `schedule-exploration` and `stateful-property-testing` own their search dimensions.

## Preserve the finding

Save raw/converted histories, initial state, model and adapter, checker/build/configuration, limits and actual result. Keep verbose partial-linearization evidence with any visualization; a picture is neither a minimal contradiction nor a root-cause proof: for a rejected history it "shows partial linearizations and illegal linearization points" ([visualization](https://raw.githubusercontent.com/anishathalye/porcupine/97cd067defd99df172053ba7f4ca5bbae57fe446/visualization.go)). Explain the contradiction from the contract and actual real-time edges, then use `evidence-based-triage` for attribution.

Reduce matched operations, setup and values while retaining their true ordering, uncertainty and selected violation; use `failure-reduction`. The paper's decision procedure does not supply a liveness check: it "considers only complete histories", justified by its assumption "that the concurrent system is deadlock-free" ([paper, p.5](https://arxiv.org/abs/1504.00204)). Read [common mistakes](references/common-mistakes.md) for invalid shortcuts.

Return the checked object guarantee, history/model scope, actual result and cost, witness/replay paths, and unresolved recorder/model assumptions. Follow the task's existing execution and publication authority.
