# Concolic and hybrid operation

## Match compiler, runtime and dependencies

The inspected SymCC README says it is "maintained in a best effort mode" and asks for LLVM "any version between 8 and 18", Z3 4.5 or later and C++17. Its CMake contains differing LLVM-range warnings ("developed for LLVM 8 through 17" and "8 through 18"), and older configuration prose uses `QSYM_BACKEND=ON/OFF` while actual compiler/runtime CMake uses `SYMCC_RT_BACKEND`, defaulting to `qsym`. Verify one fitting selected tuple rather than merge contradictory instructions ([README](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/README.md), [compiler CMake](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/CMakeLists.txt), [configuration](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/docs/Configuration.txt), [selected runtime](https://raw.githubusercontent.com/eurecom-s3/symcc-rt/892f817f38f5abfa083dd0c1caa7ced821566bf5/CMakeLists.txt)).

Keep the parent-selected runtime submodule with its compiler: at the inspected SymCC commit, `runtime` is a submodule pinned to symcc-rt `892f817f38f5abfa083dd0c1caa7ced821566bf5`, and the compiler CMake builds it with `SOURCE_DIR ${CMAKE_SOURCE_DIR}/runtime`. Existing builds use `symcc` or `sym++` as compiler wrappers ("a wrapper "sym++" around clang++"); real target and dependency code must be included ([runtime submodule](https://api.github.com/repos/eurecom-s3/symcc/contents/runtime?ref=522c48070bc312aeb621a631ff130ded71507d6d), [compiler](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/CMakeLists.txt), [C++ integration](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/docs/C%2B%2B.txt)). Compiler source headers declare GPL3-or-later, runtime headers LGPL3-or-later; they are separate component declarations ([compiler](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/CMakeLists.txt), [runtime](https://raw.githubusercontent.com/eurecom-s3/symcc-rt/892f817f38f5abfa083dd0c1caa7ced821566bf5/CMakeLists.txt)). These source snapshots are evidence, not authority for dependency changes.

With the system C++ library, "data that passes through the standard library will be concretized"; instrumented libc++ needs a matching dependency build, and the guide warns that building it "currently doesn't work with the QSYM backend", so it is built with the simple backend. A process running successfully is not evidence that symbolic influence survived the boundary ([C++ integration](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/docs/C%2B%2B.txt)).

## Run a concrete seed and validate alternatives

In an existing compatible integration, compile the real C target with `symcc`, then use the following file-input shape. The target must actually read that exact seed. Paths are owned examples, and assignments shown are POSIX shell syntax ([README, usage](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/README.md), [runtime configuration](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/docs/Configuration.txt)).

```text
SYMCC_INPUT_FILE=/absolute/seed SYMCC_OUTPUT_DIR=/absolute/results ./sym_target /absolute/seed
```

Stdin is the default symbolic source unless configured otherwise; `SYMCC_MEMORY_INPUT` is a different mode that "Can't be combined with SYMCC_INPUT_FILE". With the QSYM backend, "all input has to be available from the start", and `SYMCC_OUTPUT_DIR` (default "/tmp/output") stores new inputs "(QSYM backend only)". That backend also prunes paths, which the README says "isn't sound"; "When building with the simple backend the paths should be found." Preserve original bytes/arguments, generated files and actual target results; one run follows its concrete path and proposes alternatives for later runs ([README](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/README.md), [configuration](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/docs/Configuration.txt)).

The optional helper's documented shape is `symcc_fuzzing_helper -o AFL_OUT -a AFL_INSTANCE -n UNIQUE_LANE -- ./sym_target @@`. Its guide says "we've tested with version 2.56b" of classic AFL; selected AFL++ compatibility needs actual verification. The guide's own example names each instance and warns "just make sure that each has a unique name". Match symbolic and coverage/sanitizer/semantic builds, use distinct output identities and replay alternatives through the real oracle ([hybrid guide](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/docs/Fuzzing.txt)).

Actual helper source declares `const TIMEOUT: u32 = 90;`, runs each attempt under `timeout -k 5`, sets `SYMCC_ENABLE_LINEARIZATION` to `1` and passes its own `SYMCC_AFL_COVERAGE_MAP`, whose format follows classic AFL but "isn't meant to point at a map file that AFL uses too". Those are selected-version mechanics, not a whole-job budget, completeness guarantee or AFL's live bitmap. Record generated/admitted/oracle-evaluated/replayed cases, killed attempts and total solver/replay cost; queue-file count is not confirmed defect count ([helper producer](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/util/symcc_fuzzing_helper/src/symcc.rs), [map/input configuration](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/docs/Configuration.txt)).

## Worked boundary

For this pack's illustrative hybrid experiment, take a real decoder with a difficult field relationship. Retain its setup, compile matched symbolic and actual-oracle builds, generate alternatives from a valid seed, then check the same promised effect natively. An unsupported library, pruned branch or timed-out attempt remains an explicit limitation. The guide separates generated testcase management from vulnerability checking: "new test cases need to be checked for whether they trigger vulnerabilities"; it does not make each new input a defect ([hybrid guide](https://raw.githubusercontent.com/eurecom-s3/symcc/522c48070bc312aeb621a631ff130ded71507d6d/docs/Fuzzing.txt)). Use `corpus-evolution` for compatible exchange and `evidence-based-triage` for attribution.
