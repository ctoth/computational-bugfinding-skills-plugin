# Distributed fault testing

Choose a promised result or effect that a real deployment can violate during failure or recovery. Jepsen combines a target client, workload generator, nemesis and history checker. Its checker analyzes "the test's history for correctness", while its performance and availability graphs help "characterize how a system responds to different faults"; an outage or performance plot is not itself a consistency counterexample ([Jepsen README, intro and Design Overview](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/README.md)).

## Establish the executable experiment

Read the actual target adapter, operation/acknowledgment contract, enabled read/durability mode and checker. Keep known acknowledgments, definite no-effect failures and uncertain requests distinct: `:ok` "*must* logically affect the system", `:fail` "*must* have no logical effect", and "An `:info` may do either." Jepsen's timeout wrapper returns `(assoc op :type :info, :error ::timeout)`, not a known abort ([jepsen.history README, Operation Semantics](https://raw.githubusercontent.com/jepsen-io/history/61d2776c889ad84f7c6922977cf05e8f11970402/README.md), [jepsen.client, Timeout](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/client.clj)).

Use an existing fitting integration and owned disposable nodes. Check the selected build, dependencies, host requirements and actual runner options in [Jepsen operation](references/jepsen-operation.md). Do not substitute framework names for a working target client and oracle; node operations can alter firewalls, processes and clocks: "tests may mess with clocks, add apt repos, run killall -9 on processes" ([Jepsen README, VMs, Real Hardware, etc.](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/README.md)).

## Search an actual failure boundary

Inventory the baseline first. If concurrent histories and injected checker controls already exist, choose an additional real deployment boundary: acknowledged-write failover, a lease holder paused past ownership change, asymmetric communication, or an applicable recovery transition. Treat these as target-specific hypotheses, not generic bug claims; [fault model and activation](references/fault-model-and-activation.md) develops the experiments, and its Node.js section covers Toxiproxy, process control and MSW limits.

Specify affected nodes/roles/links, directions and timing relative to meaningful operations. Select faults supported by the target adapter. Jepsen's combined nemesis packages (partition, packet, file corruption, clock, kill/pause) come with the docstring warning "Consider this API unstable."; kill and pause modes exist only when the DB implements `db/Process` or `db/Pause`, and the file-corruption package has no final repair generator. The package "is *not* intended for complex sequences of faults"; for those, "you'll write your own generator instead" ([jepsen.nemesis.combined, ns docstring, db-generators, file-corruption-package and nemesis-package](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/nemesis/combined.clj)).

Observe fault activation independently of the request log, then observe healing. Jepsen 0.3.15 documents that `control.util/grepkill!` "has silently done nothing since 0.3.12", so kill and pause/resume faults built on it "did nothing"; a named nemesis event cannot establish that the intended fault occurred ([Jepsen CHANGELOG, 0.3.15 Bugfixes](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/CHANGELOG.md)).

## Execute through recovery and the oracle

Budget setup, calls, load, healing, final observations, analysis and teardown separately. `gen/time-limit` "will only emit operations for dt seconds" after its first operation; `--time-limit` is "Excluding setup and teardown"; and `--seed` "does not guarantee determinism in general" because behavior depends on "the timing and responses to each request" ([jepsen.generator, time-limit](https://raw.githubusercontent.com/jepsen-io/generator/3073ba45cb3db0b6dcc5aa915907a2e67b04eef5/src/jepsen/generator.clj), [jepsen.cli, test-opt-spec](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/cli.clj)).

Use the target's final repair and observation phases. The etcd producer logs "Healing cluster", runs the nemesis final generator, sleeps 10 seconds, then runs the workload's final client generator; that fixed sleep is an implementation choice, not proof another target has converged ([jepsen.etcd, etcd-test](https://raw.githubusercontent.com/jepsen-io/etcd/b47cc401f27bfb7c28afd9ac088b5f0dca4501b8/src/jepsen/etcd.clj)). The checker runs only after the database is torn down (step "7. Teardown the database" precedes step 9, "When the generator is finished, invoke the checker with the history"), so every observation the oracle needs must be a recorded operation ([jepsen.core, run!](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/core.clj)). Read [recovery and evidence](references/recovery-and-evidence.md) before teardown.

Inspect explicit checker and subchecker results, admission and witnesses. `check-safe` turns a checker exception into `{:valid? :unknown ...}`; `valid-priorities` ranks `true` 0, `:unknown` 0.5 and `false` 1, which makes a false sub-result dominate unknown in composition ([jepsen.checker, check-safe, valid-priorities and Compose](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/checker.clj)). Record the checker version: Jepsen 0.3.15 notes that Elle 0.2.8 fixed a bug that made `rw-register` workloads "incorrectly infer cyclic version orders for keys", so a verdict from an affected version needs re-analysis ([Jepsen CHANGELOG, 0.3.15 Bugfixes](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/CHANGELOG.md)). Use `linearizability-checking` or `transactional-history-testing` for the promised history model, `crash-consistency-testing` for storage-failure semantics, and `deterministic-simulation` for controlled environment replay.

## Finish with retained evidence

Return the tested guarantee, actual activated faults/topology, reached successful operations, uncertain outcomes, recovery observations, explicit verdict/witness, resource use and artifact paths. Preserve source/build/configuration, raw history and actual replay attempts; traceable observations enable inspectable contradictions but have model limits. Blind register writes "destroy history"; detected cycles "can be presented to the user as a witness of an anomaly"; yet "In practice, we typically fail to observe the results of some transactions", and "Our approach ignores predicates and deals only in individual objects" ([Elle, §§3, 4.3, 6 and 9](https://arxiv.org/abs/2003.10554v1)).

Use `failure-reduction` to shrink workload and fault sequence while retaining the same violation; use `evidence-based-triage` for attribution and `bugfinding-campaign` for further allocation. Read [common mistakes](references/common-mistakes.md) when requested faults, completed reads and checked guarantees diverge. Invocation preserves existing execution and publication authority.
