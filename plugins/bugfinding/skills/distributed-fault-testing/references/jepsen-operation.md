# Jepsen operation

These are conditional instructions for an existing target-specific Jepsen integration. Commands are illustrative, not executed examples or universal defaults. Read the selected adapter/build and its help before execution; a Jepsen library dependency does not supply an arbitrary application's client, workload or checker: "A test is a Clojure program which uses the Jepsen library" ([Jepsen README, intro and Design Overview](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/README.md)).

## Select one actual source/build set

Verify Java/Leiningen and the selected target's node requirements. The README at the pinned commit specifies a JVM "version 21 or higher", JNA, Leiningen, Gnuplot and Graphviz for a control node; DB nodes need "A TCP network", "An SSH server" and "Sudo or root access", and most tests assume more, "like running on Debian, using `iptables`". LXC "Containers don't have real clocks, so you generally can't use them to test clock skew" ([Jepsen README, Setting Up Control Nodes, VMs, Real Hardware, etc. and LXC](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/README.md)). Core `project.clj` sets `:jvm-opts ["-Xmx32g"`, so budget control-node memory from the project you run ([core project.clj](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/project.clj)).

Use the project's actual dependency manifest and artifact identity. Current source and published API documentation may differ; the inspected `project.clj` declares `(defproject jepsen "0.3.16-SNAPSHOT"` and depends on `[io.jepsen/generator "0.1.7-SNAPSHOT"]`, a snapshot rather than a release pin, while the README's AWS Marketplace instructions say "Choose version 0.3.11" for the single-VM image. Core project metadata declares "Eclipse Public License" with an EPL-1.0 URL, and the core `LICENSE.txt` is headed "Eclipse Public License -v 1.0". The separate generator and etcd READMEs declare "Eclipse Public License 2.0" with stated secondary-license conditions. Check the selected components instead of substituting one declaration for all ([core project.clj](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/project.clj), [core LICENSE.txt](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/LICENSE.txt), [Jepsen README, AWS](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/README.md), [jepsen.generator README, License](https://raw.githubusercontent.com/jepsen-io/generator/3073ba45cb3db0b6dcc5aa915907a2e67b04eef5/README.md), [jepsen.etcd README, License](https://raw.githubusercontent.com/jepsen-io/etcd/b47cc401f27bfb7c28afd9ac088b5f0dca4501b8/README.md)).

## Keep the client faithful

`open!` and `close!` must not reset logical test state: "Open *should not* affect the logical state of the test" and "Close should not affect the logical state of the test." Initialization belongs in `setup!`, "Called to set up database state for testing." Preserve the operation's function/process and translate actual results; the `Validate` wrapper checks only that a completion is a map, has `:type` `:ok`, `:info` or `:fail`, and keeps the same `:process` and `:f`, so it does not establish semantic correctness ([jepsen.client, Client protocol and Validate](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/client.clj)).

A Jepsen `:fail` completion "*must* have no logical effect on the system"; `:info` "denotes an indeterminate result", and "If a process crashes (e.g. by beginning an `:invoke` followed by an `:info`) it can never invoke an operation again" ([jepsen.history README, Operation Structure and Operation Semantics](https://raw.githubusercontent.com/jepsen-io/history/61d2776c889ad84f7c6922977cf05e8f11970402/README.md)). Retries add attempts whose effects may all land: generators can react so that "if a write fails, the generator could decide to retry it", the etcd adapter has `--retry-max-attempts`, and Elle notes "Duplicate writes can occur when a client or database retries an append operation" ([jepsen.generator README](https://raw.githubusercontent.com/jepsen-io/generator/3073ba45cb3db0b6dcc5aa915907a2e67b04eef5/README.md), [jepsen.etcd, cli-opts](https://raw.githubusercontent.com/jepsen-io/etcd/b47cc401f27bfb7c28afd9ac088b5f0dca4501b8/src/jepsen/etcd.clj), [Elle, §6.1](https://arxiv.org/abs/2003.10554v1)). Preserve actual request/attempt provenance, and use the history specialist for faithful conversion. Read the adapter's own option help too: etcd's `--client-type etcdctl` is described as "definitely buggy" and can leak "operations into the *next* test run" ([jepsen.etcd, cli-opts](https://raw.githubusercontent.com/jepsen-io/etcd/b47cc401f27bfb7c28afd9ac088b5f0dca4501b8/src/jepsen/etcd.clj)).

## Run a fitting bounded test

For an existing compatible etcd test with an owned-node file and verified register/partition options:

```text
lein run test --help
lein run test --nodes-file OWNED_NODES --workload register --nemesis partition --concurrency 2n --time-limit 60 --test-count 1 --seed 12345
```

Replace resource values and workload/fault selection from the experiment. These option shapes come from the actual CLI and target producer: `--nodes-file` is a "File containing node hostnames, one per line", `--concurrency` takes "an integer, optionally followed by n" to multiply by node count, and without node options the CLI defaults to `["n1" "n2" "n3" "n4" "n5"]`, so always pass the owned nodes ([jepsen.cli, default-nodes and test-opt-spec](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/cli.clj)). In etcd, `--serializable` "allows etcd to serve stale data" and must not be silently enabled while checking linearizable reads. Its short form is `-s` ("Use serializable reads, instead of going through consensus."), and the README's stale-read demonstration `lein run test --time-limit 30 -s --nemesis partition --workload register --concurrency 2n` uses it, so copying that line changes the read contract ([jepsen.etcd README, Quickstart and Options](https://raw.githubusercontent.com/jepsen-io/etcd/b47cc401f27bfb7c28afd9ac088b5f0dca4501b8/README.md), [jepsen.etcd, cli-opts](https://raw.githubusercontent.com/jepsen-io/etcd/b47cc401f27bfb7c28afd9ac088b5f0dca4501b8/src/jepsen/etcd.clj)).

Reserve an outer budget for the entire run. `--time-limit` is "Excluding setup and teardown"; `gen/time-limit` "will only emit operations for dt seconds", which bounds emission, not arbitrary in-flight calls. `gen/phases` wraps each phase in `synchronize`, which "waits for all workers to be free before it begins", and `until-ok` yields operations "until one of those operations completes with :type :ok", so a never-succeeding final read keeps the run going. A seed "may allow specific workloads to be more reproducible", not real timing/responses ([jepsen.cli, test-opt-spec](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/cli.clj), [jepsen.generator, time-limit, synchronize, phases and until-ok](https://raw.githubusercontent.com/jepsen-io/generator/3073ba45cb3db0b6dcc5aa915907a2e67b04eef5/src/jepsen/generator.clj)).

## Interpret and retain

The inspected single-test CLI maps `false` to exit 1 and `:unknown` to exit 2 and calls no exit for any other `:valid?` value; its usage text lists "254   Invalid arguments" and "255   Internal Jepsen error". With `--test-count` above 1 it exits on the first false or unknown run. Require actual intended-history checks and inspect `:results`, sub-results, errors and witnesses rather than treating exit 0 as sufficient ([jepsen.cli, test-usage and single-test-cmd](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/cli.clj)). `check-safe` turns checker exceptions into `:unknown`; `unbridled-optimism` always returns `{:valid? true}`; the set checker returns `:unknown` with "Set was never read" when no final read succeeded; and `stats` computes each `:f` as `(pos? oks)` ("Results are valid only if every :f has at some :ok"), which yields `false` in code although its docstring says `:unknown` ([jepsen.checker, check-safe, unbridled-optimism, stats and set](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/checker.clj)).

For failed setup, inspect actual adapter/runtime/SSH evidence; a missing client or mismatched dependency is not a target consistency finding. For unknown, retain the checker error/incomplete observations. For false, inspect the violated contract and witness. For apparent success with no activated fault or successful property evaluations, report the narrower tested space. Reanalysis through `analyze` "constructs a test map using the same arguments as `run`, but analyzes a history from disk instead": it rebuilds the checker from stored arguments and current source and does not replay the original cluster execution ([jepsen.cli, single-test-cmd](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/cli.clj)).
