# Recovery and evidence

A useful experiment includes final repair and post-recovery observations. The actual etcd producer, in its non-Antithesis branch ("In normal Jepsen, we use a time limit, then heal the cluster"), separates timed load, healing, a `(gen/sleep 10)` recovery wait and final workload operations; its literal sleep is not a universal convergence guarantee. Under Antithesis the same producer uses `jepsen.nemesis/noop` and goes straight to the final client generator, so check which branch ran ([jepsen.etcd, etcd-test](https://raw.githubusercontent.com/jepsen-io/etcd/b47cc401f27bfb7c28afd9ac088b5f0dca4501b8/src/jepsen/etcd.clj)). The generator library's own example has the same shape: `(gen/nemesis {:f :repair})`, `(gen/sleep 10)`, then `(gen/clients (gen/each-thread (gen/until-ok {:f :read})))` ([jepsen.generator README, Example](https://raw.githubusercontent.com/jepsen-io/generator/3073ba45cb3db0b6dcc5aa915907a2e67b04eef5/README.md)).

## Observe before cleanup

Use the actual adapter's repair actions, then supported readiness/convergence evidence and final reads within the authorized budget. Record unsuccessful repair and unavailable final observations separately. Nemesis final generators request `:start`/`:resume` (process), `:stop-partition`, `:stop-packet` and `:reset-clock` repair; the file-corruption package has no final generator. Those requests alone do not demonstrate the system recovered ([jepsen.nemesis.combined, db-generators, partition/packet/clock/file-corruption packages](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/nemesis/combined.clj)).

Capture the state required by the oracle before teardown, as recorded operations. `run!` captures logs, tears down the database, and only then "When the generator is finished, invoke the checker with the history"; `analyze!` passes `(:history test)` to `check-safe`, so the checker cannot query live state. Log collection kills the database "if possible, before downloading logs" unless `:leave-db-running?` is set (CLI `--leave-db-running`, "so you can inspect it"); `finally` cleanup attempts do not prove repair succeeded ([jepsen.core, snarf-logs!, run! and analyze!](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/core.clj), [jepsen.cli, test-opt-spec](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/cli.clj)).

Keep fault/cleanup operations confined to the known test-owned deployment. Adapters may control node-wide processes, firewalls and clocks ("The account you use on those boxes needs sudo access to set up DBs, control firewalls, etc."), and the README warns against pointing Jepsen "at your prod machines", so never transplant their cleanup onto unrelated shared-host resources ([Jepsen README, VMs, Real Hardware, etc.](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/README.md)).

## Preserve a replayable investigation

Retain target/client/checker/build/configuration, initial data and promised modes; actual operations and ambiguous outcomes; requested/observed fault and repair sequence; raw histories, server/client logs, final observations, explicit checker results/witnesses and resource costs. Stored test maps come "without some fields that wouldn't make sense to serialize--no `:checker`, `:client`, etc.", so keep compatible source/dependencies and arguments too ([Jepsen README, Working With the REPL](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/README.md)).

Use traceable values where they reveal the promised behavior. Explain the contradiction from actual operations and dependency evidence; model/observation limits remain even under many injected faults. Blind register writes "destroy history"; Elle presents a cycle "as a witness of an anomaly" with "a human-readable explanation"; and "Our approach ignores predicates and deals only in individual objects" ([Elle, §§3, 6 and 9](https://arxiv.org/abs/2003.10554v1)).

## Worked recovery decision

Suppose a permitted failure interrupts load and all reads time out. Healing plus a successful final observation can establish whether known acknowledged values remain; absent final observation leaves that guarantee unresolved, as Jepsen's set checker does by returning `:unknown` with "Set was never read" ([jepsen.checker, set](https://raw.githubusercontent.com/jepsen-io/jepsen/6766ba09682bcb668d44c025e687dd8b1616e8a2/jepsen/src/jepsen/checker.clj)). A stale-read option or weaker acknowledgment policy changes the premise and must be recorded. The real etcd options distinguish stale reads (`--serializable` "allows etcd to serve stale data"), lost un-fsynced writes (`--lazyfs`) and `--unsafe-no-fsync` ("This should be unsafe.") ([jepsen.etcd README, Options](https://raw.githubusercontent.com/jepsen-io/etcd/b47cc401f27bfb7c28afd9ac088b5f0dca4501b8/README.md)).

Spend the next bounded allocation on the missing activation/recovery/observation dimension, not automatically higher request volume. Report load success, ambiguity, fault coverage and checked histories separately. This allocation is the pack's design; use `bugfinding-campaign` for its broader decision.

Preserve originals while reducing workload plus fault sequence. Keep acknowledgment, failure model, recovery boundary and the same witness; losing the effect and retaining only a timeout changes the candidate. Route mechanics to `failure-reduction` and attribution to `evidence-based-triage`.
