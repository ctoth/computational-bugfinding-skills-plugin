# Evidence and observer limits

Keep original raw reports and exact input/setup/operation sequence, source/build/module/runtime identity, annotations/suppressions/options, limits, and actual replay attempts. Go reports include conflicting access and creation stacks; Helgrind distinguishes current and earlier accesses ([Go Report Format](https://raw.githubusercontent.com/golang/website/a8b66266e226994e2ead51317bace3ee83cedab9/_content/doc/articles/race_detector.html), [Helgrind §7.4](https://valgrind.org/docs/manual/hg-manual.html)).

Inspect the two accesses and real synchronization semantics. A warning around a custom primitive may reflect an incomplete observer model; an annotation must describe a genuine relation rather than invent one. The original study demonstrates this distinction in reference-count/message-queue handling ([TSan 2009, §§5,6.4, pp.65–66,68–69](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/35604.pdf)). Its historical Valgrind modes are not modern Go/Clang runtime settings.

Keep potential lock-order cycles separate from demonstrated deadlock. Preserve a true access violation even without a final crash ([Helgrind §§7.3–7.4](https://valgrind.org/docs/manual/hg-manual.html)). A downstream symptom can be far from the offending reference-count interaction ([TSan 2009, §7.1, p.69](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/35604.pdf)).

These are this pack's handoff choices: return reached sharing/lifetime paths, actual instrumentation omissions, paired report evidence, resource use, replay outcomes and remaining uncertainty. Use semantic identities when addresses vary. Reduce only while retaining the relevant lifetime, competing accesses and ordering model; preserve original evidence when replay loses accumulated state. `failure-reduction` and `evidence-based-triage` own those mechanics.

A clean reached-path detector run is bounded evidence, not a proof of unexecuted paths ([Go How to Use](https://raw.githubusercontent.com/golang/website/a8b66266e226994e2ead51317bace3ee83cedab9/_content/doc/articles/race_detector.html)). For sequential-object/transaction guarantees use `linearizability-checking`/`transactional-history-testing`; for controlled choices use `schedule-exploration`. Timing failures and process growth need their own contract/evidence, not automatic deadlock/leak labels ([Go Runtime Overhead](https://raw.githubusercontent.com/golang/website/a8b66266e226994e2ead51317bace3ee83cedab9/_content/doc/articles/race_detector.html), [TSan limitations](https://raw.githubusercontent.com/llvm/llvm-project/635f30899dd0914fa89f0b3dc9a9e548e6d0ceec/clang/docs/ThreadSanitizer.md)).
